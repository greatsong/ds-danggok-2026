0. 왜 배우나

인터넷 게시판, 메신저, 온라인 쇼핑몰 — 여러 사람이 함께 쓰는 서비스의 뒤에는 예외 없이 데이터베이스가 있습니다. 우리가 한 학기 동안 다룬 CSV 파일은 혼자 분석하기에는 충분했지만, 이제 상황이 달라집니다. 중간고사가 끝나면 시작하는 팀 프로젝트에서는 2~3명이 같은 데이터를 동시에 쌓고 고쳐야 합니다. 그 도구를 오늘 익힙니다. 그리고 사실, 여러분은 이미 한 학기 내내 데이터베이스를 써 왔습니다 — 작품을 올리고 서로 피드백을 남긴 우리 갤러리가 바로 그것입니다.

1. 개념 이해 — 데이터셋, 데이터베이스, 테이블

📖 교과서의 정의 『데이터 과학』 25~27쪽

"데이터셋(dataset)이란 하나의 주제에 대한 여러 데이터들이 모인 집합(set)을 말한다." (25쪽)

"데이터베이스(database)는 여러 사람이 공유하여 사용하기 위해 통합 관리되는 데이터의 집합으로, 데이터베이스 시스템을 사용하면 대규모의 데이터를 효율적으로 저장하고 검색하며, 업데이트하고 관리할 수 있다." (26쪽)

"데이터베이스에는 여러 종류의 데이터셋이 들어가는데, 이때 각각의 데이터셋은 표 형태로 저장되며 이를 테이블(table)이라고 한다." (27쪽)

→ 우리가 쓰던 CSV 파일 하나가 데이터셋. 그것을 여러 사람이 공유하도록 통합 관리하는 것이 데이터베이스이고, 그 안의 표 하나하나가 테이블이다.

CSV 파일 하나가 데이터셋, 그것을 여럿이 공유하도록 모아 관리하는 것이 데이터베이스, 그 안의 표 하나하나가 테이블입니다.

정의의 핵심은 "여러 사람이 공유하여"입니다. 혼자 쓸 때는 파일이면 충분한데, 여럿이 함께 쓰는 순간 파일은 세 가지 한계에 부딪힙니다.

부족해지는 순간CSV 파일이라면데이터베이스라면
동시에 쓰기두 사람이 같은 파일을 고쳐 저장하면 한쪽의 작업이 덮여 사라진다여러 사람의 기록이 각각 한 행으로 안전하게 들어간다
계속 쌓기새 글이 올 때마다 파일을 열어 고치고 다시 저장해야 한다새 데이터가 자동으로 누적된다
골라 읽기전체를 내려받아 눈으로 찾아야 한다조건에 맞는 것만 즉시 검색해 가져온다
🔬 움직여 보기 — "동시에 쓰기", 파일과 테이블에서 각각 벌어지는 일

그림을 클릭할 때마다 한 단계씩 움직입니다 — ① A가 적는다 → ② 그 사이 B도 적는다 → ③ 저장 — 두 결과를 비교합니다.

위 표의 첫 줄 "동시에 쓰기"가 일어나는 실제 순서입니다. 오늘 실습 ②에서 옆자리 친구와 직접 재현합니다.

교과서 26쪽은 데이터베이스의 이점을 네 가지로 정리합니다 — 편리한 버전 관리, 데이터 무결성 유지, 데이터 보안 강화, 체계적인 데이터 관리. 누가 언제 고쳤는지 기록이 남고, 이상한 값의 입력을 막고, 사용자별로 권한을 나누고, 조건 검색이 된다는 뜻입니다. 그리고 데이터베이스가 하는 일은 결국 네 동작 — 데이터를 생성하고, 읽고, 갱신하고, 삭제하는 것(29쪽) — 으로 요약됩니다. 오늘 기본 실습에서 "생성"과 "읽기"를 직접 하고, 이어지는 도전에서 "갱신"과 "삭제"까지 네 동작을 모두 채웁니다.

💡 수파베이스 — 우리가 쓸 데이터베이스

수파베이스(Supabase)는 웹에서 테이블을 만들고 앱과 연결할 수 있는 데이터베이스 서비스입니다. 수업에서는 선생님이 미리 만들어 둔 학급 공용 프로젝트에 접속 정보만 받아 연결합니다. 수업 도입에서 교과서 31쪽 탐구활동의 쇼핑몰 테이블 설계를 수파베이스 화면으로 직접 확인합니다 — 속성 이름, 데이터형, 조건이 교과서의 설계표 그대로 화면에 나타납니다.

2. 실습 — 내 앱에 방명록 달기 (바이브 코딩)

그림에는 주요 열만 그렸습니다. 실제 표에는 도전 과제에서 쓰는 비밀번호 열이 하나 더 있습니다.

1차시에 배포한 내 포트폴리오 앱에 방명록 페이지를 추가합니다. 방문자가 남긴 글이 수파베이스의 방명록 테이블에 쌓이고, 쌓인 글이 목록으로 나타나는 것이 목표입니다.

  1. ① 샘플 프롬프트 — 그대로 붙여 넣기

    내 앱에 방명록 페이지를 추가해 줘.

    pages/13_방명록.py
    # pages/13_방명록.py — 수파베이스 표에 글을 남기고 읽는다
import streamlit as st
from supabase import create_client

st.header("방명록")


@st.cache_resource
def connect():
    # 접속 정보는 코드가 아니라 비밀 금고에 둔다
    return create_client(st.secrets["SUPABASE_URL"], st.secrets["SUPABASE_KEY"])


db = connect()

with st.form("write"):
    name = st.text_input("이름")
    message = st.text_input("한 줄 소감")
    password = st.text_input("네 자리 비밀번호", type="password", max_chars=4)
    sent = st.form_submit_button("남기기")

if sent:
    if not name.strip() or not message.strip():
        st.warning("이름과 소감을 모두 적어 주세요.")          # 빈 칸이면 저장하지 않는다
    else:
        db.table("guestbook").insert({
            "name": name.strip(), "message": message.strip(), "password": password
        }).execute()
        st.success("남겼습니다.")
        st.rerun()

rows = db.table("guestbook").select("*").order("created_at", desc=True).execute().data
for row in rows:
    st.write(f"**{row['name']}** — {row['message']}")
    st.caption(row["created_at"])

새로고침해도 글이 남아 있습니다. 친구의 컴퓨터에서 열어도 같은 글이 보입니다. 지금까지 우리의 데이터는 내 컴퓨터 속 파일이었지만, 이 순간부터는 인터넷 위의 공동 저장소입니다. 그리고 ③에서 빈 칸 저장을 막은 것은 교과서 26쪽의 "데이터 무결성 유지"를 직접 구현한 것입니다 — 잘못된 값이 들어오지 않도록 제약을 거는 일입니다.

# 도전 — 비밀번호가 맞을 때만 고치고 지운다 (방명록 페이지에 이어 붙일 부분)
for row in rows:
    with st.expander(f"{row['name']} — {row['message']}"):
        확인 = st.text_input("비밀번호", type="password", key=f"pw{row['id']}")
        새글 = st.text_input("새 소감", value=row["message"], key=f"msg{row['id']}")
        c1, c2 = st.columns(2)
        if c1.button("고치기", key=f"edit{row['id']}"):
            if 확인 == row["password"]:
                db.table("guestbook").update({"message": 새글}).eq("id", row["id"]).execute()
                st.rerun()
            else:
                st.error("비밀번호가 다릅니다.")
        if c2.button("지우기", key=f"del{row['id']}"):
            if 확인 == row["password"]:
                db.table("guestbook").delete().eq("id", row["id"]).execute()
                st.rerun()
            else:
                st.error("비밀번호가 다릅니다.")
💡 판단 — 왜 비밀번호가 필요한가

고치기·지우기 단추를 아무 조건 없이 달면, 누구든 남의 글을 지울 수 있게 됩니다. 갱신과 삭제는 데이터를 바꾸는 동작이라 "누가 할 수 있는가"라는 권한의 문제가 반드시 따라옵니다 — 교과서 26쪽의 "데이터 보안 강화"가 실습에서 처음으로 필요해지는 순간입니다. 실제 서비스는 이 권한 규칙을 데이터베이스에 세워 둡니다. 우리 학급 공용 프로젝트에도 선생님이 같은 성격의 규칙을 미리 설정해 두었습니다.

3. SQL — 테이블을 다루는 언어

②에서 AI가 준 코드에는 db.table("guestbook").select("*").order("created_at", desc=True) 같은 줄이 있었습니다. 이 한 줄은 데이터베이스가 알아듣는 문장 하나를 파이썬으로 옮긴 것입니다. 그 원래 문장이 SQL(Structured Query Language, 구조화 질의 언어)입니다. 수파베이스 화면의 SQL 편집기에 그대로 쳐 넣을 수 있고, AI가 짜 준 코드의 뜻을 읽어 내는 근거이기도 합니다. 문장을 외우는 것이 목적이 아닙니다. 네 동작(생성·읽기·갱신·삭제)이 어떤 문장으로 표현되는지 읽을 수 있으면 됩니다. 수파베이스처럼 표(테이블) 형태로 데이터를 관리하는 데이터베이스를 관계형 데이터베이스라 하고, 관계형 데이터베이스는 대부분 SQL로 다룹니다.

읽기 — SELECT 한 문장의 네 낱말

가장 자주 쓰는 문장입니다. 어느 테이블에서(FROM) 어느 열을(SELECT) 가져올지 말하고, 필요하면 조건(WHERE)과 정렬(ORDER BY)을 덧붙입니다. 대문자로 쓴 낱말이 명령어이고 나머지가 테이블 이름과 열 이름입니다.

SQL · 읽기
-- 방명록의 이름·소감·작성 시각을 최신순으로 가져온다
SELECT name, message, created_at
FROM guestbook
ORDER BY created_at DESC;

-- 모든 열(*)을 가져오되, 이름이 '민수'인 글만
SELECT * FROM guestbook WHERE name = '민수';
낱말뜻우리말로 읽으면
SELECT가져올 열을 고른다. *는 모든 열"이름과 소감 열만 보여 줘"
FROM어느 테이블에서 가져올지"방명록 표에서"
WHERE조건에 맞는 행만 남긴다"이름이 민수인 것만"
ORDER BY정렬 기준. DESC는 내림차순, ASC는 오름차순"최신 글부터"

1절에서 본 세 번째 한계 "골라 읽기"가 바로 WHERE입니다. 파일이라면 전체를 내려받아 눈으로 찾아야 했던 일을, 데이터베이스는 조건 한 줄로 해냅니다.

생성·갱신·삭제 — 네 동작이 네 문장으로

SQL · 생성 · 갱신 · 삭제
-- 생성(C): 새 글 한 줄을 넣는다. id와 created_at은 자동으로 채워진다
INSERT INTO guestbook (name, message, password)
VALUES ('민수', '방명록이 생겨서 신기해요', '1234');

-- 갱신(U): 7번 글의 소감을 고친다
UPDATE guestbook SET message = '정말 신기해요' WHERE id = 7;

-- 삭제(D): 7번 글을 지운다
DELETE FROM guestbook WHERE id = 7;
⚠️ WHERE가 없는 UPDATE·DELETE

UPDATE와 DELETE에서 WHERE를 빼면 테이블의 모든 행이 바뀌거나 지워집니다. 도전 과제의 코드가 .eq("id", row["id"])로 글 번호 하나를 정확히 가리킨 까닭입니다. 실제 서비스가 갱신·삭제 권한을 엄격히 나누는 것(데이터 보안 강화)도 같은 이유입니다.

표 만들기 — 교과서 31쪽 설계표가 그대로 문장이 된다

교과서 31쪽 탐구활동은 쇼핑몰의 사용자·제품·장바구니 테이블을 속성명·설명·데이터형·조건으로 설계합니다. 우리 방명록 표를 같은 양식으로 적으면 아래와 같고, 이 설계표는 CREATE TABLE 문장 한 개로 옮겨집니다. 선생님이 학급 공용 프로젝트에 방명록 표를 만들 때 실행한 문장과 같은 구조입니다.

속성명설명데이터형조건
id글 번호정수자동 증가 · 중복 불가(기본 키)
name작성자 이름문자열비워 둘 수 없음
message한 줄 소감문자열비워 둘 수 없음

SQL · 표 만들기
CREATE TABLE guestbook (
  -- 정수 · 자동 증가 · 기본 키
  id         bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  -- 문자열 · 비워 둘 수 없음
  name       text NOT NULL,
  message    text NOT NULL,
  password   text,
  -- 날짜·시각 · 저장 시각이 자동으로 들어감
  created_at timestamptz DEFAULT now()
);
-- 권한 정책을 켠다 (이후 정책으로 허용한 동작만 통과한다)
ALTER TABLE guestbook ENABLE ROW LEVEL SECURITY;

속성명열 이름name, message

조건NOT NULL(비워 둘 수 없음) · PRIMARY KEY(기본 키) · UNIQUE(중복 불가) · DEFAULT(기본값)이메일은 UNIQUE

기본 키(primary key)는 행 하나를 유일하게 가리키는 열입니다. 같은 이름의 사람이 두 번 글을 남겨도 id가 다르므로 두 행을 구별할 수 있습니다. 갱신과 삭제가 "7번 글"처럼 행 하나를 정확히 가리킬 수 있는 것도 기본 키 덕분입니다. 교과서 31쪽의 설계표에서 "조건" 칸에 적는 내용이 바로 이런 제약입니다.

    SQL과 내 코드의 대응
    
  
    AI가 짜 준 방명록 코드는 SQL 문장을 직접 쓰지 않고 파이썬 함수로 같은 뜻을 전합니다. 두 표현은 한 줄씩 대응합니다. 코드를 읽다가 막히면 이 표로 SQL 문장으로 되돌려 읽습니다.
    
  
    
    
    동작SQL방명록 코드(파이썬)
    
    
      
    읽기SELECT * FROM guestbook ORDER BY created_at DESCdb.table("guestbook").select("*").order("created_at", desc=True)
    
      
    생성INSERT INTO guestbook (name, message, password) VALUES (…)db.table("guestbook").insert({…})
    
      
    갱신UPDATE guestbook SET message = … WHERE id = 7db.table("guestbook").update({…}).eq("id", 7)
    
      
    삭제DELETE FROM guestbook WHERE id = 7db.table("guestbook").delete().eq("id", 7)
    
        
  
    

  
    묶어서 세기 — GROUP BY와 집계
    
  
    분석 질문의 대부분은 "무엇별로 얼마나"의 꼴입니다. 12차시의 급식 154일이 meals 테이블(열: 날짜 · 월 · 요일 · 식사 · 메뉴 · 칼로리)에 들어 있다고 합시다. 손으로 세었던 값들은 SQL 한 줄로 셀 수 있고, "요일별 평균 열량"처럼 묶어서 세는 질문은 GROUP BY 한 줄로 답합니다.
    
  
    SQL · 세기와 묶기
    -- 배추김치가 나온 중식은 며칠인가 (연관 분석의 "기본 등장률"의 분자 → 86)
SELECT COUNT(*) FROM meals WHERE 식사 = '중식' AND 메뉴 LIKE '%배추김치%';

-- 요일별로 묶어 일수와 평균 열량을 구하고, 평균이 높은 요일부터 다섯 줄만
SELECT 요일, COUNT(*) AS 일수, AVG(칼로리) AS 평균칼로리
FROM meals
WHERE 식사 = '중식'
GROUP BY 요일
ORDER BY 평균칼로리 DESC
LIMIT 5;
    
  
    
    
    낱말뜻
    
    
      
    COUNT(*)조건에 맞는 행의 개수를 센다
    
      
    LIKE '%배추김치%'문자열 안에 "배추김치"가 들어 있는 행을 찾는다. %는 "무엇이든"
    
      
    GROUP BY같은 값끼리 묶는다. "요일별로"
    
      
    COUNT · SUM · AVG · MAX · MIN묶음마다 개수 · 합계 · 평균 · 최댓값 · 최솟값
    
      
    AS결과 열에 붙일 이름
    
      
    LIMIT앞에서 몇 행만 가져온다. "상위 5개"
    
        
  
    
  
    
    🔬 움직여 보기 — SQL 문장 조립기 (급식 20끼 연습 데이터)
    
    
      
    아래에서 낱말을 고르면 SQL 문장이 만들어지고, 그 문장을 연습용 급식 20끼(15일의 중식 15끼와 석식 5끼) 표에 실행한 결과가 바로 아래에 나타납니다. 칼로리는 연습용 예시 값입니다. 조건 없이 요일로 묶으면 같은 날의 중식과 석식이 따로 세어지므로, "일수"를 보려면 조건에서 식사를 고릅니다.
    
      
    
        
        
        
        
        
      
    
      
    만들어진 SQL
    
      
    
      
    묶는 열을 바꾸면 결과 표의 행 수가 바뀝니다. 묶은 열이 아닌 열(예: 날짜)은 한 칸에 여러 값이 들어가야 하므로 SELECT에 그대로 쓸 수 없고, 집계 함수로 감싸야 합니다. 이 규칙이 GROUP BY의 핵심입니다.
    
    
    
  
    


  
    실생활 앱에서 SQL이 하는 일 — 인스타그램으로 읽기

    앱에서 하는 일뒤에서 실행되는 SQL읽는 법
    
    
      
    피드를 연다SELECT * FROM posts ORDER BY 올린시각 DESC LIMIT 20;게시물 표에서, 올린 시각이 늦은 것부터, 20개만

    ❤ 좋아요를 누른다UPDATE posts SET 좋아요 = 좋아요 + 1 WHERE id = 4;4번 게시물 한 행의 좋아요 값을 1 늘린다
    
      
    댓글을 단다INSERT INTO comments (게시물id, 작성자, 댓글) VALUES (4, 'dog_bori', '박스 안이 그렇게 좋아?');댓글 표에 새 행 하나를 넣는다

    이야기 — 영양사 선생님의 부탁
    
  
    
    
    🍱 급식부의 두 사람과 SQL 편집기
    
    
    학생회 급식부의 지우와 민수에게 영양사 선생님이 부탁을 하나 합니다. "금요일 급식이 유독 무겁다는 의견이 급식 게시판에 여러 번 올라왔어요. 느낌인지 사실인지 확인하고 싶은데, 지난 학년도 식단 154일이 meals 테이블에 들어 있으니 요일별로 열량을 비교해 줄 수 있을까요?" 두 사람은 12차시에 급식 규칙을 찾을 때 썼던 바로 그 데이터를 엽니다. 이번에는 파이썬 대신 SQL 편집기입니다.
    
  
    
  
    
    
    장면 1 지우가 먼저 나섭니다. "요일별로(GROUP BY) 평균 열량을 내서(AVG), 높은 요일부터(ORDER BY) 보면 되겠다." 지우가 써야 할 SQL 문장을 종이에 완성해 본 뒤 펼쳐 보세요. 중식만 대상으로 하고, 결과 열의 이름은 요일과 평균칼로리로 합니다.
    
    
    정답 펼쳐 보기
      
    SELECT 요일, AVG(칼로리) AS 평균칼로리 FROM meals WHERE 식사 = '중식' GROUP BY 요일 ORDER BY 평균칼로리 DESC; — 위 조립기에서 묶는 열 "요일", 집계 "AVG(칼로리)", 조건 "식사 = '중식'"을 고르면 같은 문장이 만들어집니다.
    
    
    
  
    
  
    
    
    장면 2 옆에서 민수가 "요일마다 급식이 며칠씩 있었는지도 같이 보여 드리자"며 문장을 하나 더 씁니다. SELECT 요일, 날짜 FROM meals WHERE 식사 = '중식' GROUP BY 요일; 실행 단추를 누르자 빨간 오류 문장이 뜹니다. 지우가 화면을 보더니 말합니다. "요일로 묶었는데 날짜를 그대로 달라고 하면, 한 칸에 서른 개 넘게 어떻게 넣어?" 오류의 까닭은 무엇일까요?
    
    
    
      
    
        
        
        
      
    
      
    뜻에 맞게 고치면 SELECT 요일, COUNT(*) AS 일수 FROM meals WHERE 식사 = '중식' GROUP BY 요일;입니다. WHERE가 GROUP BY 앞에 오는 것은 올바른 순서입니다.
    
    
    
  
    
  
    
    
    💡 이야기의 끝 — 숫자가 나온 뒤에 남는 판단
    
    
    두 문장을 합쳐 실행하니 금요일 29일의 평균이 912kcal로 가장 높고, 화요일 32일의 평균이 852kcal로 가장 낮았습니다(요일별 일수는 154일 실측, 칼로리는 연습용 예시 값). 지우는 "금요일이 정말 무겁네요"라고 말하려다 멈춥니다. 60kcal 차이가 "유독 무겁다"고 말할 만큼 큰 차이인지, 금요일에 특식이 몇 번 있었던 것은 아닌지, 표만으로는 알 수 없기 때문입니다. SQL은 세는 일을 대신하지만, 그 수가 무엇을 뜻하는지는 1차시부터 배운 대로 사람이 판단합니다.
    
  
    

  
    권한 정책 — 표가 기본적으로 닫혀 있는 까닭
    
  
    수파베이스의 표는 처음부터 아무나 읽고 쓸 수 있는 것이 아닙니다. 표마다 누가 어떤 동작을 할 수 있는가를 정책으로 정해 둡니다(행 수준 보안, RLS). 정책이 없으면 모든 출입이 막혀 있고, 만들어 둔 정책만 통과합니다. 우리 학급 방명록 표에는 선생님이 수업에 필요한 동작(읽기·추가, 도전 과제를 위한 갱신·삭제)을 정책으로 열어 두었습니다. 그래서 도전 과제의 비밀번호 확인은 데이터베이스가 아니라 앱 안에서 하는 검사입니다. 실제 서비스라면 "자기 글만 고칠 수 있다"는 규칙을 정책으로 데이터베이스에 세웁니다. 교과서 26쪽의 "데이터 보안 강화"가 실제 도구에서 구현되는 자리가 바로 이 정책입니다.
    
  
    
    
    ⚠️ 바이브 코딩에서 가장 자주 만나는 DB 오류
    
    
    "연결은 됐는데 저장이 안 된다"의 첫째 원인은 권한 정책이고, 둘째 원인은 AI가 표 이름이나 열 이름을 지어낸 것입니다. AI는 우리 표가 어떻게 생겼는지 볼 수 없습니다. 오류 문장에 permission, policy, not found, column이 보이면 코드보다 먼저 표 이름·열 이름·권한을 확인합니다.
    
  
    

  
    AI에게 DB를 주문할 때 알려 줄 네 가지
    
  
    SQL 문장을 직접 쓰지 않더라도, AI가 데이터베이스 코드를 맞게 짜려면 AI가 볼 수 없는 사실을 프롬프트에 적어 주어야 합니다. 2절의 ① 샘플 프롬프트에 이미 네 가지가 다 들어 있었습니다.
    
  
    
    
    알려 줄 것왜①의 문장
    
    
      
    표 이름과 열 이름(필요하면 데이터형)AI는 표를 볼 수 없다. 이름이 한 글자만 달라도 저장되지 않는다"표 이름은 guestbook이고 열은 name · message · created_at · password야"
    
      
    새 표를 만들지 말 것학급 공용 프로젝트에서는 학생이 표를 만들 권한이 없다"새 표를 만들지 말고 이 표에 그대로 연결해 줘"
    
      
    접속 정보는 비밀 금고에주소와 키가 코드에 박히면 공개 저장소로 새어 나간다"접속 정보는 비밀 금고에 넣어 줘"
    
      
    무결성 조건빈 값이나 잘못된 값이 들어가지 않게"빈 칸으로 제출하면 저장하지 말고 안내 문구를 보여 줘"
    
        
  
    
  
    팀 프로젝트에서 "설문 응답을 팀 표에 모아 장르별 평균을 보여 줘" 같은 주문을 할 때도 같은 네 가지를 적으면 됩니다. 무엇을 만들지와 표의 생김새는 사람이 말하고, SQL 문장과 코드는 AI가 씁니다. 나온 결과가 맞는지는 이 절의 문장을 읽을 수 있는 사람만 확인할 수 있습니다.
    

  
    
    🔎 심화 — 표와 표를 잇는 열(외래 키)과 JOIN
    
    
      
    교과서 31쪽 쇼핑몰 설계에서 장바구니 표는 사용자 표의 id와 제품 표의 id를 열로 가집니다. 다른 표의 기본 키를 가리키는 이 열을 외래 키라 하고, 두 표를 이 열로 이어 붙이는 문장이 JOIN입니다. 같은 정보를 두 표에 중복해서 적지 않아도 되는 것이 데이터베이스가 표를 여러 개로 나누는 까닭입니다.
    
      
    SQL · JOIN
    -- 장바구니에 담긴 제품의 이름과 수량을, 장바구니 표와 제품 표를 제품 id로 이어서 가져온다
SELECT 장바구니.사용자id, 제품.제품명, 장바구니.수량
FROM 장바구니
JOIN 제품 ON 장바구니.제품id = 제품.id;
    
      
    지필 범위에서는 외래 키가 "표와 표를 잇는 열"이라는 뜻까지만 알면 됩니다. JOIN 문장을 쓰는 연습은 팀 프로젝트에서 표가 둘 이상 필요해질 때 합니다.
    
    
    
  
    

  
    4. 팀 프로젝트 예고 — 데이터로 답할 수 있는 문제인가
    
  
    공통 수업은 다음 시간 데이터 윤리 한 차시가 남았습니다. 중간 지필평가 이후에는 2~3인 팀으로 한 학기의 도구 전부를 들고 팀만의 질문에 도전합니다. 오늘은 그 준비로 팀을 구성하고 주제 후보를 고릅니다.
    
  
    
    
    📖 교과서의 정의 『데이터 과학』 174쪽
    
    
    "데이터 과학은 다양한 분야의 문제를 해결하고 의사 결정을 지원하는 데 큰 도움이 되지만, 모든 문제를 해결할 수 있는 것은 아니다." (174쪽)
    
    
    → 그래서 주제를 고를 때는 세 가지를 차례로 묻는다 — 데이터가 충분히 있는가 · 그 데이터가 문제 해결에 적합한가 · 법적·윤리적으로 올바른가.
    
  
    
  
    세 번째 물음의 기준 네 가지(개인정보 · 출처 · 이용 약관 · 편향)는 다음 시간 데이터 윤리에서 세웁니다. 오늘 고른 후보는 다음 시간에 그 기준으로 다시 점검합니다. 데이터가 아무리 많아도 윤리 관문을 통과하지 못하면 프로젝트 주제가 될 수 없습니다. 프로젝트의 5주 흐름·팀 저장소·개인의 몫은 팀 프로젝트 안내에 정리되어 있습니다. 팀에서는 다음 순서로 주제 카드를 만듭니다.
    
  
      
    
    • 팀 구성(2~3인) — 관심 질문이 비슷한 사람끼리
      • 
    
    • 틀 고르기 — 회귀·분류·군집·연관 중 팀의 질문에 맞는 분석 틀은 무엇인가
      • 
    
    • 데이터 후보 3개 — 각 후보를 앞의 두 물음으로 먼저 판단해 보기 (교과서 176쪽 탐구활동). 세 번째 물음은 다음 시간에
      • 
  
    
  
    5. 개념 정리 — 파일에서 공동 저장소로
    
  
    오늘 배운 것을 한 줄로 정리하면 이렇습니다. 혼자 읽는 데이터는 파일이면 되지만, 여럿이 동시에 쌓는 데이터에는 데이터베이스가 필요하다. 그리고 그 필요는 팀 프로젝트가 시작되는 순간 현실이 됩니다.
    
  
    1차시에 질문 던지기로 시작한 공통 수업이 이제 한 시간 남았습니다. 질문을 세우고 첫 앱을 배포하고(1차시), API로 데이터를 구해 오고(2·5차시), 그래프로 데이터를 읽고(3·4차시), 회귀·분류·군집·연관의 네 가지 틀로 모델을 만들고 평가했으며(6~12차시), 오늘 여럿이 함께 쓰는 저장소까지 갖췄습니다. 다음 시간에는 이 전 과정을 윤리의 기준으로 점검하고 공통 수업을 마무리합니다.
    

  
    6. 확인 문제
    
  
    
    
    문제 1 모둠 과제 자료를 CSV 파일로 만들어 메신저로 주고받는 방식과 비교해, 데이터베이스를 쓸 때의 이점을 두 가지 서술해 본 뒤 펼쳐 보세요.
    
    
    예시 답 펼쳐 보기
      
    ① 여러 사람이 동시에 데이터를 입력해도 서로의 작업을 덮어쓰지 않고 각각의 기록이 안전하게 쌓인다(파일은 마지막에 저장한 사람이 이전 내용을 덮을 수 있다). ② 데이터가 한곳에 계속 누적되고, 필요한 것만 조건으로 검색해 읽을 수 있다(파일은 최신본이 무엇인지 헷갈리고 전체를 열어 찾아야 한다). 이 밖에 수정 기록이 남는 버전 관리, 잘못된 값을 막는 무결성 유지, 사용자별 접근 권한 설정도 이점이다.
    
    
    
  
    
  
    
    
    문제 2 데이터셋, 데이터베이스, 테이블 — 세 용어를 우리 실습의 예에 대응해 봅니다.
    
    
    
      
    우리 실습에서 테이블에 해당하는 것은?
    
      
    
        
        
        
      
    
      
    데이터베이스(수파베이스 프로젝트) 안에 표 형태로 저장된 데이터셋 하나가 테이블입니다. 급식 CSV 파일은 데이터베이스 밖의 파일 하나 — 데이터셋이고, 수파베이스 프로젝트는 테이블들을 담는 쪽 — 데이터베이스입니다.
    
    
    
    
    세 용어의 관계 펼쳐 보기
      
    데이터셋은 하나의 주제에 대한 데이터의 집합으로, 우리가 쓰던 급식 CSV 파일 하나가 데이터셋이다. 데이터베이스는 여러 사람이 공유하도록 데이터를 통합 관리하는 집합으로, 우리 학급의 수파베이스 프로젝트가 그것이다. 데이터베이스 안에서 각 데이터셋은 표 형태로 저장되는데 이것이 테이블이며, 오늘 만든 방명록 표가 테이블 하나에 해당한다.
    
    
    
  
    
  
    
    
    문제 3 어느 팀이 "우리 학교 학생들의 등하교 위치 기록을 모아 시간대별 이동 패턴을 분석하겠다"는 주제를 제안했습니다. 주제 판단의 세 물음 중 이 주제가 걸리는 곳은?
    
    
    
      
    
        
        
        
      
    
      
    데이터가 있다는 것과 써도 된다는 것은 다릅니다. 개인을 추적할 수 없는 형태로 바꾸어 다시 설계해야 합니다.
    
    
    
  
    

  
    🎒 오늘의 체크
    
  
      
    
    • CSV 파일로 부족해지는 세 순간(동시에 쓰기·계속 쌓기·골라 읽기)을 말할 수 있다.
      • 
    
    • 내 앱에 방명록 페이지를 달고, 남긴 글이 목록에 쌓이는 것을 확인했다.
      • 
    
    • 친구의 앱에 글을 남겨 "우리의 저장소"가 된 것을 확인했다.
      • 
    
    • (읽기 자료) SQL 문장 하나를 읽고 네 동작(생성·읽기·갱신·삭제) 중 어느 것인지 말할 수 있다.
      • 
    
    • 팀을 구성하고, 데이터 후보를 앞의 두 물음으로 먼저 판단해 주제 카드 초안을 냈다.
      • 
  
    

  
    📚 오늘의 용어
    
  
    
    
    용어뜻
    
    
    데이터셋하나의 주제에 대한 여러 데이터가 모인 집합 (예: CSV 파일 하나)
    
    
    데이터베이스여러 사람이 공유하여 사용하도록 통합 관리되는 데이터의 집합
    
    
    테이블데이터베이스 안에 표 형태로 저장된 데이터셋 하나
    
    
    수파베이스웹에서 테이블을 만들고 앱과 연결하는 데이터베이스 서비스. 우리 갤러리의 뼈대
    
    
    데이터 무결성잘못된 값이 들어오지 않도록 제약을 걸어 데이터의 올바름을 지키는 것
    
    
    데이터 적합성어떤 문제가 데이터로 답할 수 있는 문제인지 — 존재·적합·윤리로 판단
    
    
    SQL테이블에 데이터를 넣고(INSERT) 꺼내고(SELECT) 고치고(UPDATE) 지우라고(DELETE) 지시하는 언어. WHERE는 조건, ORDER BY는 정렬
    
    
    기본 키행 하나를 유일하게 가리키는 열(예: 방명록의 id). 갱신·삭제가 행 하나를 정확히 가리키는 근거
    
    
    GROUP BY같은 값끼리 묶어 묶음마다 COUNT·AVG 같은 집계를 구하는 SQL 낱말. 묶은 열이 아닌 열은 집계 함수로 감싼다
    
    
    권한 정책(RLS)표마다 누가 어떤 동작을 할 수 있는지 정해 둔 규칙. 정책이 없으면 모든 출입이 막힌다
