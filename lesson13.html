0. 왜 배우나

여러 사람이 함께 쓰는 서비스는 데이터베이스로 기록을 관리할 수 있습니다. 반찬 월드컵에서도 서로 다른 기기에서 보낸 대결 기록을 한곳에 모아 읽어야 합니다. 파일로도 저장 기능을 만들 수 있지만, 동시 입력과 검색·접근 권한을 관리하는 일이 복잡해집니다. 오늘은 Supabase의 PostgreSQL 데이터베이스를 이용해 이 과정을 익힙니다.

1. 개념 이해 — 데이터셋, 데이터베이스, 테이블

📖 교과서의 정의 『데이터 과학』 25~27쪽

"데이터셋(dataset)이란 하나의 주제에 대한 여러 데이터들이 모인 집합(set)을 말한다." (25쪽)

"데이터베이스(database)는 여러 사람이 공유하여 사용하기 위해 통합 관리되는 데이터의 집합으로, 데이터베이스 시스템을 사용하면 대규모의 데이터를 효율적으로 저장하고 검색하며, 업데이트하고 관리할 수 있다." (26쪽)

"데이터베이스에는 여러 종류의 데이터셋이 들어가는데, 이때 각각의 데이터셋은 표 형태로 저장되며 이를 테이블(table)이라고 한다." (27쪽)

→ 급식 CSV는 데이터셋을 담은 한 가지 형태입니다. 이번에 사용하는 관계형 데이터베이스는 데이터를 테이블로 관리합니다. Supabase 프로젝트는 데이터베이스와 앱 연결 기능 등을 제공하며, 그 안의 대결 기록 표가 하나의 테이블입니다.

위 그림의 대결 기록 표는 일부 열만 보여 줍니다. 실제로는 판 번호·라운드·겨룬 두 반찬도 함께 저장합니다.

여러 사람이 파일 사본을 주고받거나 파일 전체를 덮어쓰는 방식은 아래와 같은 문제가 생길 수 있습니다. 데이터베이스는 동시 처리, 조건 검색, 제약과 접근 권한을 관리하는 기능을 제공합니다. 이 기능들도 앱과 데이터베이스에 올바르게 설정해야 합니다.

파일 사본을 각각 수정해 덮어쓰는 상황을 단순화한 모식도입니다. 실습에서는 두 사람이 각각 대결을 마친 뒤 새로 조회해 두 기록이 모두 저장되었는지 확인합니다.

교과서 26쪽의 무결성 유지·보안 강화·체계적 관리 등의 이점을 실습과 연결해 봅니다. 기록의 변경 이력을 보존하려면 별도의 이력 관리나 백업 설정도 필요합니다. 데이터를 생성·읽기·갱신·삭제하는 네 동작을 CRUD라고 합니다. 월드컵 앱에서는 생성과 읽기·집계를, 아래 SQL 시뮬레이터에서는 갱신과 삭제를 연습합니다.

💡 수파베이스 — 우리가 쓸 데이터베이스

Supabase는 PostgreSQL 데이터베이스와 API·인증 등의 기능을 제공합니다. 이번에는 교사 또는 모둠 대표 한 명이 연습용 프로젝트와 대결 기록 표를 준비합니다. 다른 학생은 같은 프로젝트에 연결합니다. 아래 준비 절차부터 따라가면 실제로 여러 기기의 대결 기록을 한곳에 저장하고 집계할 수 있습니다.

파일은 형식이 정한 크기 한도를 넘으면 기록이 조용히 사라집니다. 데이터베이스는 행을 계속 추가하고 제약을 어기면 오류로 알립니다. 반찬 월드컵 앱에서 저장 결과를 확인하지 못했을 때 재선택을 잠그도록 만든 처리도 같은 이유에서 필요합니다.

2. 실습 — 반찬 월드컵과 대결 기록 분석 (바이브 코딩)

대결 한 번이 한 행입니다. id(기록 번호) · game_id(한 판을 묶는 번호) · round(라운드) · left_menu · right_menu · winner · created_at만 저장하며 이름·학번·비밀번호는 받지 않습니다.

오늘 실습에서는 좋아하는 반찬을 1대1로 겨루는 8강 토너먼트를 만듭니다. 한 판은 8강 네 번, 4강 두 번, 결승 한 번으로 모두 일곱 번 선택합니다. 각 대결의 결과는 표의 한 행으로 저장되며, 이 행들은 학급이 함께 쓰는 데이터베이스에 쌓입니다. 판이 쌓이면 학급 전체의 대결 기록이 되고, 이 기록을 뒤에서 분석합니다.

5차시에서 배운 급식 API 집계 방법을 적용하여 후보를 선정합니다. 조회 기간은 2025년 9월부터 2026년 9월까지이며, 중식 184일 동안의 자료를 대상으로 합니다. 밥과 김치와 국과 후식을 걸러 낸 뒤 남은 주요리 가운데 자주 나온 여덟 가지를 후보로 정합니다. 아래 후보는 수업에 사용할 목록으로 고정합니다. 같은 기간을 다시 조회해도 원자료가 수정되거나 반찬 이름 정리·제외 기준이 다르면 결과가 달라질 수 있으므로, 비교할 때는 같은 저장본과 처리 기준을 사용합니다.

  1. 1. Supabase 프로젝트를 만듭니다
    Supabase 대시보드에 로그인합니다. 사용할 조직을 선택하고 New project로 연습용 프로젝트를 만듭니다. 프로젝트 이름·DB 비밀번호·지역 등 화면에서 요구하는 항목을 입력하고 준비가 끝날 때까지 기다립니다. 이 DB 비밀번호는 아래 앱에 넣을 API 키와 다른 값입니다.
  2. 2. 대결 기록 표와 권한을 준비합니다
    만든 프로젝트의 SQL Editor에서 새 쿼리를 엽니다. 3절의 ‘SQL · 표 만들기’ 코드 전체를 복사해 붙여 넣고 Run을 누릅니다. 표 생성부터 권한 정책까지 한 번만 실행합니다. 이미 표가 있다는 오류가 나오면 반복 실행하거나 기존 표를 지우지 말고, 올바른 연습용 프로젝트를 열었는지 먼저 확인합니다.
  3. 3. 준비 결과를 확인합니다
    Table Editor에서 public 스키마의 menu_duels를 엽니다. id·game_id·round·left_menu·right_menu·winner·created_at 일곱 열과 RLS 활성화 상태를 확인합니다. 새로 만든 표는 0행입니다. SQL 실행 중 오류가 있었다면 그대로 앱 연결로 넘어가지 않습니다.
  4. 4. 같은 프로젝트의 주소와 키를 복사합니다
    프로젝트의 Connect에서 Project URL과 publishable 키를 확인합니다. 키는 Settings → API Keys에서도 찾을 수 있습니다. 사용할 값은 https://…supabase.co 형식의 프로젝트 주소와 sb_publishable_… 키입니다. DB 연결 문자열이나 DB 비밀번호를 넣지 않습니다. secret·service_role 키도 사용하지 않습니다. 준비 담당자가 직접 앱을 배포하거나, 앱을 만들 학생에게 이 두 값을 전달합니다.

화면 이름이나 위치가 달라졌다면 Supabase 프로젝트·SQL 준비 안내와 API 키 안내를 확인합니다.

  1. 준비 — 비밀 금고(secrets)에 넣을 접속 정보 두 줄 만들기
    준비 담당자가 확인한 프로젝트 주소와 publishable 키로 아래 두 줄을 만듭니다. 코드 파일 대신 앱의 Secrets에 넣습니다. 처음 배포할 때는 Advanced settings → Secrets에 붙여 넣고 저장합니다. 이미 배포했다면 앱의 설정에서 Secrets를 수정합니다. 자세한 배포 순서는 아래 ‘앱 배포’ 안내를 따릅니다.
    Secrets에 넣을 두 줄의 모양
    SUPABASE_URL = "준비한 프로젝트 주소를 여기에"
SUPABASE_KEY = "준비한 publishable 키를 여기에"
    🔐 두 줄 만들기 — 준비한 값을 붙여 넣으면 Secrets에 넣을 두 줄이 완성됩니다
    SUPABASE_URL = "…" SUPABASE_KEY = "…"
    스트림릿 클라우드 열기 ↗
    주소와 키는 이 화면 안에서만 쓰이고 어디에도 저장·전송되지 않습니다. 복사한 두 줄을 처음 배포할 때의 Advanced settings → Secrets 또는 배포된 앱의 Secrets 설정에 붙여 넣습니다. 연결 정보는 교사가 안내한 범위에서 사용합니다.
    ⚠️ 이름 세 곳 일치 — 하나라도 다르면 못 찾는다

    SUPABASE_URL과 SUPABASE_KEY는 비밀 금고와 코드에서 철자가 같아야 합니다. 이 실습에는 publishable 키 또는 기존 anon 키를 사용합니다. secret·service_role 키는 학생에게 배포하지 않습니다. 공개 가능한 키를 숨기는 것만으로 데이터를 보호할 수는 없으며, 실제 허용 동작은 데이터베이스의 권한과 RLS 정책으로 정합니다.

8강 토너먼트로 진행해 줘. 판을 시작할 때 후보 순서를 섞고, 두 반찬을 나란히 보여 준 뒤 하나를 고르게 해.

    main.py
    # main.py — 반찬 월드컵 8강. 대결 한 번이 표의 한 행이 된다.
import random
import uuid

import streamlit as st
from supabase import create_client

MENUS = ["제육볶음", "간장찜닭", "가자미순살튀김", "돈육불백",
         "미트볼데리야끼볶음", "수육", "진미채고추장볶음", "치즈떡닭갈비"]
ROUND = {8: "8강", 4: "4강", 2: "결승"}

st.header("🏆 반찬 월드컵")
st.caption("이름 없이 참여하는 연습 게임입니다. 대결 기록 수는 참여 인원과 다릅니다.")


@st.cache_resource
def connect():
    return create_client(st.secrets["SUPABASE_URL"], st.secrets["SUPABASE_KEY"])


try:
    db = connect()
except Exception:
    st.error("연결 정보를 확인하세요. 선생님이 표와 권한을 준비한 뒤 연결합니다.")
    st.stop()


def new_game():
    order = MENUS[:]
    random.shuffle(order)                      # 대진표를 판마다 섞는다
    st.session_state.game_id = uuid.uuid4().hex
    st.session_state.queue = order             # 이번 라운드에서 겨룰 차례
    st.session_state.winners = []              # 이번 라운드에서 이긴 반찬
    st.session_state.size = len(order)         # 이번 라운드의 크기 (8·4·2)
    st.session_state.save_pending = False


if "queue" not in st.session_state:
    new_game()

# 이번 라운드가 끝났으면 다음 라운드를 준비한다
if not st.session_state.queue and len(st.session_state.winners) > 1:
    st.session_state.queue = st.session_state.winners
    st.session_state.winners = []
    st.session_state.size = len(st.session_state.queue)

def choose(winner, left, right, round_name):
    st.session_state.save_pending = True
    try:
        db.table("menu_duels").insert({
            "game_id": st.session_state.game_id,
            "round": round_name,
            "left_menu": left,
            "right_menu": right,
            "winner": winner,
        }).execute()
    except Exception:
        # 통신 오류여도 DB에는 저장되었을 수 있어 재제출을 잠근다
        st.rerun()
    st.session_state.save_pending = False
    st.session_state.winners.append(winner)
    st.session_state.queue = st.session_state.queue[2:]
    st.rerun()


if not st.session_state.queue:                 # 결승까지 끝났다
    st.success("우승: " + st.session_state.winners[0])
    if st.button("다시 하기"):
        new_game()
        st.rerun()
else:
    left, right = st.session_state.queue[0], st.session_state.queue[1]
    round_name = ROUND[st.session_state.size]
    st.subheader(round_name)
    if st.session_state.save_pending:
        st.warning("저장 결과를 확인하지 못했습니다. 재선택을 잠갔습니다. 선생님에게 확인하세요.")
    col_l, col_r = st.columns(2)
    if col_l.button(left, use_container_width=True, disabled=st.session_state.save_pending):
        choose(left, left, right, round_name)
    if col_r.button(right, use_container_width=True, disabled=st.session_state.save_pending):
        choose(right, left, right, round_name)

st.caption("판 번호: " + st.session_state.game_id)
st.caption("반복 참여를 막지는 않습니다. 저장 결과 확인이 필요하면 이 판 번호를 준비 담당자에게 알려 주세요.")

    한 판이 끝나면 우승 반찬 하나가 남습니다. 우승만으로는 그 반찬이 정말 인기 있는지 알 수 없습니다. 토너먼트에서는 이긴 반찬만 다음 라운드로 올라갑니다. 그 결과 다음 라운드에 진출한 반찬은 겨룬 횟수가 많아집니다. 승리 수와 함께 이긴 횟수를 겨룬 횟수로 나눈 비율인 승률을 살펴봅니다. 승률도 상대와 대진표의 영향을 받으므로 학급 전체의 선호 비율로 해석하지 않습니다.

    ③ 개선
    이 앱에 학급 전체의 대결 기록을 분석하는 화면을 추가해 줘.
menu_duels에 저장된 전체 기록을 대상으로 해. id, game_id, round, left_menu, right_menu, winner 여섯 열을 읽어서 반찬별 대결 수·승리 수·승률·우승 횟수를 비교하게 해 줘.
대결 수는 left_menu와 right_menu 양쪽을 모두 세고, 우승 횟수는 round가 '결승'인 행의 winner를 세어 줘.
모든 후보를 표시하고 대결 기록이 없는 후보의 승률은 아직 알 수 없다고 안내해 줘.
승률은 백분율로 보여 주고 높은 순서의 표와 가로 막대그래프로 비교해 줘.
그래프는 plotly로 그려 줘.

한 판이 끝난 화면에서도 분석을 볼 수 있게 하고 결과를 다시 불러오는 단추를 넣어 줘.

    앞 코드 끝에 이어 붙입니다. 실제 데이터베이스의 저장·조회 결과는 배포 후 확인합니다.

    main.py에 이어 붙일 부분
    # main.py에 이어 붙일 부분 — 학급의 대결 기록을 분석한다
import pandas as pd
import plotly.express as px

st.divider()
st.subheader("학급 대결 기록")

st.button("결과 새로 불러오기")
try:
    # 조회 시작 때의 마지막 id까지만, 빠짐없이 나누어 읽는다
    latest = db.table("menu_duels").select("id").order("id", desc=True).limit(1).execute().data
    upper = latest[0]["id"] if latest else 0
    records = []
    after = 0
    while after < upper:
        page = (db.table("menu_duels")
                .select("id,game_id,round,left_menu,right_menu,winner")
                .gt("id", after).lte("id", upper).order("id").limit(500).execute().data)
        if not page:
            raise RuntimeError("마지막 기록까지 조회하지 못했습니다.")
        records.extend(page)
        after = page[-1]["id"]
except Exception:
    st.error("기록을 불러오지 못했습니다.")
    st.stop()

if not records:
    st.info("아직 대결 기록이 없습니다.")
    st.stop()

duels = pd.DataFrame(records)
# 겨룬 횟수는 왼쪽과 오른쪽을 모두 센다
fought = pd.concat([duels["left_menu"], duels["right_menu"]]).value_counts()
won = duels["winner"].value_counts()
champion = duels[duels["round"] == "결승"]["winner"].value_counts()

board = pd.DataFrame({"겨룬 횟수": fought, "이긴 횟수": won, "우승": champion}).reindex(MENUS).fillna(0).astype(int)
board["승률(%)"] = (board["이긴 횟수"] / board["겨룬 횟수"].where(board["겨룬 횟수"] > 0) * 100).round(1)
board = board.sort_values("승률(%)", ascending=False).reset_index(names="반찬")

st.caption("대결 " + str(len(duels)) + "번 · 기록이 있는 판 " + str(duels["game_id"].nunique()) + "개")
st.caption("결승 기록이 있는 판 " + str(duels.loc[duels["round"] == "결승", "game_id"].nunique()) + "개 · 진행 중 기록도 포함합니다.")
st.caption("대결이 없는 후보의 승률은 비어 있습니다. 대결 수와 판 수는 참여 인원이 아닙니다.")
st.dataframe(board, hide_index=True, width="stretch")

fig = px.bar(board.dropna(subset=["승률(%)"]).sort_values("승률(%)"), x="승률(%)", y="반찬", orientation="h",
             text="승률(%)", color="승률(%)", color_continuous_scale="Oranges",
             title="반찬별 승률")
fig.update_layout(coloraxis_showscale=False, yaxis_title="")
st.plotly_chart(fig, width="stretch")
st.caption("조회 도중 들어온 새 기록은 다시 불러오면 반영됩니다. 승률은 대진표와 반복 참여의 영향을 받습니다.")

오늘 만드는 반찬 월드컵과 구조가 같습니다. 대결 한 번이 표의 한 행으로 저장됩니다(INSERT). 그 행들을 이긴 쪽 기준으로 묶어 세면(GROUP BY·COUNT) 승률이 나옵니다. 여러 사람이 서로 다른 기기에서 남긴 기록을 한곳에 모아야 하므로 개인 파일이 아니라 공유 데이터베이스가 필요합니다.

3. SQL — 테이블을 다루는 언어

예시 코드의 db.table("menu_duels").select(...)는 파이썬에서 API를 통해 데이터 조회를 요청하는 표현입니다. 같은 조회 목적을 데이터베이스에서 표현하는 언어가 SQL입니다. 오늘은 명령어를 모두 외우기보다 어떤 표의 어떤 행을 읽거나 바꾸는 문장인지 이해합니다. 수정·삭제 예시는 별도의 연습 자료에서만 다룹니다.

읽기 — SELECT 한 문장의 네 낱말

가장 자주 쓰는 문장입니다. 어느 테이블에서(FROM) 어느 열을(SELECT) 가져올지 말하고, 필요하면 조건(WHERE)과 정렬(ORDER BY)을 덧붙입니다. 대문자로 쓴 낱말이 명령어이고 나머지가 테이블 이름과 열 이름입니다.

SQL · 읽기
-- 최근 대결 20건의 이긴 반찬과 저장 시각을 읽는다
SELECT id, winner, created_at
FROM menu_duels
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 제육볶음이 이긴 대결만 읽는다
SELECT * FROM menu_duels WHERE winner = '제육볶음';
낱말뜻우리말로 읽으면
SELECT가져올 열을 고른다. *는 모든 열메뉴와 저장 시각을 보여 주십시오.
FROM어느 테이블에서 가져올지"대결 기록 표에서"
WHERE조건에 맞는 행만 남긴다"제육볶음을 선택한 표만"
ORDER BY정렬 기준입니다. DESC는 내림차순, ASC는 오름차순입니다."최근 대결부터"

WHERE는 조건에 맞는 행을 고르는 절입니다. 파일도 프로그램으로 필터링할 수 있습니다. 데이터베이스에서는 검색 조건을 서버에 보내 필요한 결과를 가져옵니다.

생성·갱신·삭제 — 네 동작이 네 문장으로

SQL · 생성 · 갱신 · 삭제
-- 아래는 별도 연습용 표(votes_practice)를 가정한 읽기 예시이다.
-- 공용 대결 기록 표에서는 실행하지 않는다.
-- 생성(C): 새 표를 한 행 추가한다.
INSERT INTO votes_practice (menu) VALUES ('제육볶음');

-- 갱신(U): id가 7인 표의 선택을 바꾼다.
UPDATE votes_practice SET menu = '비빔밥' WHERE id = 7;

-- 삭제(D): id가 7인 표를 지운다.
DELETE FROM votes_practice WHERE id = 7;
⚠️ WHERE가 없는 UPDATE·DELETE

UPDATE·DELETE에서 WHERE를 생략하면 해당 권한으로 처리할 수 있는 모든 행이 대상이 됩니다. 행 번호 조건은 범위를 좁히지만, 누가 바꿀 수 있는지를 보장하는 인증·권한 검사는 아닙니다. 실제 공용 대결 기록 표에는 학생용 수정·삭제 권한을 부여하지 않습니다.

표 만들기 — 교과서 31쪽 설계표가 그대로 문장이 된다

교과서 31쪽의 속성명·설명·데이터형·조건 양식으로 대결 기록 표를 설계합니다. 아래 SQL은 교사 또는 모둠 대표가 연습용 프로젝트에 표와 권한을 준비할 때 사용할 코드입니다. 아직 설정을 실행했다는 뜻은 아닙니다. 학생은 표와 열 이름을 읽고 앱의 입력이 어느 열에 저장되는지 확인합니다.

CREATE TABLE public.menu_duels (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  game_id text NOT NULL CHECK (length(btrim(game_id)) > 0),
  round text NOT NULL CHECK (round IN ('8강', '4강', '결승')),
  left_menu text NOT NULL CHECK (left_menu IN ('제육볶음', '간장찜닭', '가자미순살튀김', '돈육불백', '미트볼데리야끼볶음', '수육', '진미채고추장볶음', '치즈떡닭갈비')),
  right_menu text NOT NULL CHECK (right_menu IN ('제육볶음', '간장찜닭', '가자미순살튀김', '돈육불백', '미트볼데리야끼볶음', '수육', '진미채고추장볶음', '치즈떡닭갈비')),
  winner text NOT NULL,
  CHECK (left_menu <> right_menu),
  CHECK (winner IN (left_menu, right_menu)),

);

    묶어서 세기 — GROUP BY와 집계
    
  
    대결 기록의 반찬별 승리 수는 SELECT winner, COUNT(*) FROM menu_duels GROUP BY winner;로 집계할 수 있습니다. 아래에서는 12차시의 급식 자료가 meals 표에 들어 있다고 가정해 요일별로 묶어 봅니다. 칼로리는 원래 저장본에 없는 열이므로 연습용 예시 값을 사용합니다.
    
  
    SQL · 세기와 묶기
    -- 배추김치가 나온 중식은 며칠인가 (12차시 184일 저장본에서는 102일)
SELECT COUNT(*) FROM meals WHERE 식사 = '중식' AND 메뉴 LIKE '%배추김치%';

-- 요일별로 묶어 일수와 평균 열량을 구하고, 평균이 높은 요일부터 다섯 줄만
SELECT 요일, COUNT(*) AS 일수, AVG(칼로리) AS 평균칼로리
FROM meals
WHERE 식사 = '중식'
GROUP BY 요일
ORDER BY 평균칼로리 DESC
LIMIT 5;

    🍱 급식부의 두 사람과 SQL 편집기
    
    
    다음은 SQL을 읽기 위한 가상 상황입니다. 급식부의 지우와 민수는 요일별 평균 열량을 비교하려고 합니다. 12차시의 184일 식단에 연습용 열량 값을 붙여 meals 표를 만들었다고 가정합니다. 실제 급식 영양을 평가하는 자료는 아니며, 아래 조립기의 20끼 자료와도 구분합니다.
    
  
    
  
    
    
    장면 1 지우가 먼저 나섭니다. "요일별로(GROUP BY) 평균 열량을 내서(AVG), 높은 요일부터(ORDER BY) 보면 되겠다." 지우가 써야 할 SQL 문장을 종이에 완성해 본 뒤 펼쳐 보세요. 중식만 대상으로 하고, 결과 열의 이름은 요일과 평균칼로리로 합니다.
    
    
    정답 펼쳐 보기
      
    SELECT 요일, AVG(칼로리) AS 평균칼로리 FROM meals WHERE 식사 = '중식' GROUP BY 요일 ORDER BY 평균칼로리 DESC;위 조립기에서 묶는 열 '요일', 집계 'AVG(칼로리)', 조건 '식사 = '중식''을 고르면 같은 문장이 만들어집니다.
    
    
    
  
    
  
    
    
    장면 2 옆에서 민수가 "요일마다 급식이 며칠씩 있었는지도 같이 보여 드리자"며 문장을 하나 더 씁니다. SELECT 요일, 날짜 FROM meals WHERE 식사 = '중식' GROUP BY 요일; 실행 단추를 누르자 빨간 오류 문장이 뜹니다. 지우가 화면을 보더니 말합니다. "요일로 묶었는데 날짜를 그대로 달라고 하면, 한 칸에 서른 개 넘게 어떻게 넣어?" 오류의 까닭은 무엇일까요?
    
    
    
      
    
        
        
        
      
    
      
    뜻에 맞게 고치면 SELECT 요일, COUNT(*) AS 일수 FROM meals WHERE 식사 = '중식' GROUP BY 요일;입니다. WHERE가 GROUP BY 앞에 오는 것은 올바른 순서입니다.
    
    
    
  
    
  
    
    
    💡 이야기의 끝 — 숫자가 나온 뒤에 남는 판단
    
    
    이 이야기에서는 금요일 34일의 평균이 912kcal, 화요일 39일의 평균이 852kcal라고 가정합니다. 일수는 184일 저장본, 열량은 연습용 수치입니다. 이 차이만으로 실제 금요일 급식의 적절성을 평가할 수는 없습니다. SQL은 집계를 수행하며, 결과의 의미를 판단하려면 자료의 출처와 조건을 확인해야 합니다.
    
  
    

  
    권한 정책 — 허용할 동작을 명시하는 이유
    
  
    RLS는 활성화된 테이블에서 어떤 행에 접근할 수 있는지 정하는 정책입니다. 일반 앱 역할에는 테이블 권한과 해당 정책이 모두 필요합니다. RLS가 꺼져 있거나 관리자 권한을 사용하면 정책의 보호 범위가 달라집니다. 이번 설계는 로그인 없는 연습용으로 읽기·추가만 허용하며, 누구나 그 권한으로 여러 판을 반복할 수 있다는 한계가 있습니다. 앱의 단추 숨기기는 DB 권한 검사를 대신하지 못합니다. Supabase RLS 문서에서 원리를 확인할 수 있습니다.
    
  
    
    
    ⚠️ 바이브 코딩에서 가장 자주 만나는 DB 오류
    
    
    연결·저장·조회 오류의 원인은 다를 수 있습니다. 표 이름과 열 이름, 접속 대상, 허용된 동작, RLS 정책을 순서대로 확인합니다. 오류를 없애려고 관리자 키를 넣거나 모든 권한을 열지 말고, 필요한 동작만 교사와 확인합니다.
    
  
    

  
    AI에게 DB를 주문할 때 알려 줄 네 가지
    
  
    SQL 문장을 직접 쓰지 않더라도, AI가 데이터베이스 코드를 맞게 짜려면 AI가 볼 수 없는 사실을 프롬프트에 적어 주어야 합니다. 2절의 ① 샘플 프롬프트에 이미 네 가지가 다 들어 있었습니다.
    
  
    
    
    알려 줄 것왜①의 문장
    
    
      
    표 이름과 열 이름(필요하면 데이터형)AI는 표를 볼 수 없다. 이름이 한 글자만 달라도 저장되지 않는다."표 이름은 menu_duels이고 public 스키마에 있어. 이 표의 열 이름은 id, game_id, round, left_menu, right_menu, winner, created_at 일곱 가지야"
    
      
    새 표를 만들지 말 것학급 공용 프로젝트에서는 학생이 표를 만들 권한이 없다"새 표를 만들지 말고 이 표에 그대로 연결해 줘"
    
      
    접속 정보는 비밀 금고에주소와 키가 코드에 박히면 공개 저장소로 새어 나간다"접속 정보는 비밀 금고(secrets)의 SUPABASE_URL과 SUPABASE_KEY에서 읽어 줘"
    
      
    무결성 조건빈 값이나 잘못된 값이 들어가지 않게"서로 다른 두 후보 중 하나를 골랐을 때만, 교사가 준비한 표에 대결을 한 행씩 저장해 줘"
    
        
  
    
  
    팀 프로젝트에서도 앱의 목적, 실제 표의 구조, 접속 정보의 이름, 허용된 입력과 동작을 알려 줍니다. 코드를 받은 뒤에는 저장한 값과 조회·집계 결과가 맞는지 작은 예로 확인합니다.
    

  
    
    🔎 심화 — 표와 표를 잇는 열(외래 키)과 JOIN
    
    
      
    교과서 31쪽 쇼핑몰 설계에서 장바구니 표는 사용자 표의 id와 제품 표의 id를 열로 가집니다. 다른 표의 기본 키를 가리키는 이 열을 외래 키라 하고, 두 표를 이 열로 이어 붙이는 문장이 JOIN입니다. 같은 정보를 두 표에 중복해서 적지 않아도 되는 것이 데이터베이스가 표를 여러 개로 나누는 까닭입니다.
    
      
    SQL · JOIN
    -- 장바구니에 담긴 제품의 이름과 수량을, 장바구니 표와 제품 표를 제품 id로 이어서 가져온다
SELECT 장바구니.사용자id, 제품.제품명, 장바구니.수량
FROM 장바구니
JOIN 제품 ON 장바구니.제품id = 제품.id;
    
      
    여기서는 외래 키가 "표와 표를 잇는 열"이라는 뜻까지만 알면 됩니다. JOIN 문장을 쓰는 연습은 팀 프로젝트에서 표가 둘 이상 필요해질 때 합니다.

    5. 개념 정리 — 파일에서 공동 저장소로
    
  
    데이터베이스는 여러 사람이 데이터를 저장·조회하고 함께 관리할 수 있게 합니다. 오늘은 한 대결을 저장하는 작업과 반찬별 집계를 구분하고, 앱의 검사와 데이터베이스 제약·권한이 각각 어떤 역할을 하는지 확인했습니다. 데이터의 목적에 맞는 표를 설계하는 일이 앱 개발의 출발점입니다.

    예시 답 펼쳐 보기
      
    동시 입력을 처리하는 기능으로 여러 대결 기록을 각각 저장할 수 있습니다. 한곳에 모인 데이터를 조건에 따라 조회·집계할 수 있습니다. 제약과 접근 권한도 관리할 수 있지만 올바른 설정이 필요합니다. 파일에서도 프로그램을 만들면 이런 작업이 가능하며, 데이터베이스는 이를 관리하는 기능을 제공합니다.
    
    
    
  
    
  
    
    
    문제 2 데이터셋, 데이터베이스, 테이블 — 세 용어를 우리 실습의 예에 대응해 봅니다.
    
    
    
      
    우리 실습에서 테이블에 해당하는 것은?
    
      
    
        
        
        
      
    
      
    이번 실습에서 menu_duels는 대결 기록을 행과 열로 저장하는 테이블입니다. Supabase 프로젝트는 이 테이블을 담은 데이터베이스 등을 제공하고, 급식 CSV는 데이터셋을 담은 파일입니다.
    
    
    
    
    세 용어의 관계 펼쳐 보기
      
    데이터셋은 분석할 데이터의 집합이며 급식 CSV는 이를 담는 한 가지 형태입니다. Supabase 프로젝트는 데이터베이스 등을 제공하고, 그 안의 menu_duels는 대결 기록을 저장하는 테이블입니다. 테이블은 관계형 데이터베이스에서 데이터를 행과 열로 관리하는 구조입니다.
