Ⅱ. 데이터 준비와 분석 · 5차시

API의 이해 · 우리 학교 급식을 내 앱에

"데이터는 내려받는 것만이 아니다 — 필요할 때마다 주문해서 받을 수도 있다."
이 수업의 관통 습관 — 2차시(반정형 데이터)에서 예고한 실물을 오늘 만납니다

2차시에 급식 식단표는 정형, 급식 사진은 비정형, 그리고 "급식 API 응답은 반정형"이라고 예고만 하고 지나갔습니다. 오늘 그 실물을 직접 봅니다. 파일을 하나도 내려받지 않고, 오늘 점심 식단이 내 스트림릿 앱에 나타나는 순간까지 갑니다.

🎯 오늘 하는 것
  • 주소창 실험 — 브라우저 주소창에서 급식 API를 호출해 JSON 원문을 눈으로 확인
  • 바이브 코딩 — 날짜를 고르면 그날 식단이 나오는 급식 페이지를 내 앱에 추가
  • 관찰 — 식단표에는 없던 칼로리·알레르기·원산지 정보가 API 응답 속에 있다는 것

0. 왜 배우나

버스 도착 알림, 날씨 앱, 실시간 환율 — 이런 앱들은 데이터 파일을 미리 내려받아 두지 않습니다. 여러분이 화면을 여는 순간, 앱이 데이터를 가진 서버에 요청을 보내고 응답을 받아 보여 줍니다. 이 창구가 API입니다. 2차시에 공공데이터포털에서 CSV 파일을 내려받아 봤다면, 오늘은 데이터를 받는 두 번째 방법을 배웁니다. 한 번 익혀 두면 급식·영화·날씨·대중교통 등 세상의 수많은 실시간 데이터가 여러분 앱의 재료가 됩니다. 팀 프로젝트에서 "항상 최신인 데이터"를 다루고 싶다면 오늘이 그 출발점입니다.

1. 개념 이해 — API는 키오스크 주문 창구

API는 카페나 매점의 키오스크와 같습니다. 정해진 기계(창구)에서 정해진 화면의 양식대로 주문(요청)을 넣으면, 정해진 결과물(응답)이 돌아옵니다. 키오스크에서 음료를 주문하는 일과, 내 앱이 오늘 급식을 받아 오는 일은 정확히 같은 흐름 — 요청 → 응답 — 입니다. 우리는 주방 안에서 무슨 일이 일어나는지 몰라도 음료를 받고, 나이스(NEIS) 서버 내부를 몰라도 급식 데이터를 받습니다.

🔬 더 알아보기 — API가 뭐예요? 키오스크에서 음료 주문하기로 이해하기 (클릭해서 움직여 보세요)

API는 "정해진 양식을 채워 보내면, 원하는 결과물을 정해진 형식으로 돌려주는 창구"입니다. 아래 두 줄은 클릭할 때마다 한 단계씩 움직입니다 — ①주문 입력 → ②전송 → ③만들기 → ④받기. 키오스크 음료 주문과 내 앱의 급식 받기가 똑같이 요청 → 응답으로 흐릅니다.

응답에는 상태코드라는 번호표가 함께 옵니다. 셋만 기억하면 됩니다 — 200 성공 · 404 없음(없는 메뉴를 주문한 것, 주소 오류) · 429 과다 요청(주문 폭주 — 잠깐 쉬기).

내려받기와 API는 무엇이 다를까요? 내려받은 CSV는 그 시점의 복사본입니다. 내일 식단이 바뀌어도 내 파일은 모릅니다. API는 호출할 때마다 서버가 지금 가진 데이터를 보내 주므로 항상 최신이고, 날짜나 학교를 지정해 필요한 만큼만 받을 수 있습니다.

"반정형 데이터는 일부분이 정형화된 데이터로, 구조가 존재하지만 구조를 바꿀 수도 있는 유연한 형태의 데이터를 말한다." (20쪽)

"대표적인 반정형 데이터로는 XML(eXtensible Markup Language)과 JSON(JavaScript Object Notation)이 있다." (20쪽)

"이러한 반정형 데이터는 데이터 구조를 쉽게 변경할 수 있고, 필요한 경우 표 형태로도 쉽게 변환할 수 있어 데이터 공유에 많이 활용된다." (20쪽)

→ API가 서빙하는 응답이 바로 이 JSON이다. "표로 쉽게 변환할 수 있다"는 문장을 오늘 실습에서 직접 확인한다.

JSON — 라벨 붙은 상자

API가 돌려주는 JSON은 {"라벨": 값} 짝으로 이루어진 상자입니다. 상자 안에 상자를 넣을 수 있어서, 복잡한 데이터도 층층이 담을 수 있습니다. 오늘 쓸 급식 API의 실제 응답 일부를 봅니다.

실제 응답 (일부 발췌)
{
  "mealServiceDietInfo": [
    { "head": [ { "list_total_count": 1 } ] },
    { "row": [
        {
          "SCHUL_NM": "당곡고등학교",
          "MLSV_YMD": "20260821",
          "DDISH_NM": "친환경현미밥 <br/>근대된장국 <br/>제육볶음 (5.6.10.13)...",
          "CAL_INFO": "796.4 Kcal",
          "ORPLC_INFO": "쌀 : 국내산 ..."
        }
    ] }
  ]
}
  • 값 꺼내기 = 라벨을 따라 들어가기 — 겉상자 mealServiceDietInfo 안의 목록에서 row를 꺼내고, 그 안의 DDISH_NM(식단)을 꺼내는 식입니다. "상자에서 상자를 꺼내라"고 말할 수 있으면 JSON을 읽을 수 있습니다.
  • 👀 눈여겨볼 것 — 숫자가 따옴표에 싸여 있다. "CAL_INFO": "796.4 Kcal" — 칼로리가 숫자가 아니라 따옴표 친 글자로 옵니다. 글자인 채로는 크기 비교·정렬·그래프가 되지 않으므로, 숫자로 바꾸는 한 단계가 꼭 필요합니다. 3차시에 배운 전처리가 API 데이터에서도 반복되는 것입니다.
  • 표로 바꾸면 정형이 된다 — 교과서 20쪽의 "필요한 경우 표 형태로도 쉽게 변환할 수 있다"가 바로 이 작업입니다. row 목록의 상자 하나가 표의 행 하나가 됩니다.

2. 주소창 실험 — 반정형 데이터의 실물

코드를 쓰기 전에, API가 정말 "주소로 주문하는 창구"인지 브라우저로 확인합니다. 선생님이 나눠 준 요청 주소를 주소창에 붙여 넣으면, 꾸며지지 않은 JSON 원문이 화면에 그대로 나타납니다. 중괄호와 따옴표 사이에서 다음을 찾아보세요.

  • 학교를 가리키는 조건 — 교육청 코드 B10(서울), 학교 코드 7010073(당곡고). 주소 속 이 두 값이 "우리 학교 것으로 주세요"라는 주문입니다.
  • 이름표와 값의 쌍 — 메뉴가 담긴 항목, 칼로리가 담긴 CAL_INFO, 원산지가 담긴 ORPLC_INFO. 열 이름이 표 머리글이 아니라 데이터 안에 이름표로 붙어 있습니다. 이것이 반정형의 생김새입니다.
  • 날짜 조건을 바꾸면 — 주소 속 날짜를 다른 날로 고쳐 다시 접속하면 응답이 그날 것으로 바뀝니다. 같은 창구, 다른 주문서입니다.
응답 속 이름표담긴 것급식실 식단표에는?
메뉴 항목메뉴 이름 + 알레르기 유발 식품 번호메뉴 이름만 있음

💡 인증키가 없으면 어떻게 되나

이 API는 인증키 없이도 날짜별 1일 조회는 가능합니다. 그러나 키 없이 긴 기간을 한 번에 조회하면 첫 5행만 반복되는 샘플 응답이 돌아옵니다. 제대로 쓰려면 키가 필요합니다 — 키 이야기는 5절에서 다시 합니다.

3. 실습 — 급식 페이지를 내 앱에 추가한다 (바이브 코딩)

4차시에 배포한 내 스트림릿 앱에 두 번째 페이지를 답니다. 인증키는 선생님이 나눠 주며, 코드에 직접 쓰지 않고 스트림릿의 비밀값 보관함(secrets)에 넣습니다.

✅ 여기까지 되었는지 확인
  • 날짜 선택 상자에서 오늘을 고르면 오늘 식단이 나타난다.
  • 인증키가 코드 안에 보이지 않는다 — 비밀값 보관함에서 읽어 온다.
  • 급식이 없는 날짜를 골랐을 때 앱이 안내 문구를 표시한다.
⚠️ 발견 — 내려받지 않았는데 점심이 뜬다

화면에 나타난 오늘 식단은 내 컴퓨터 어디에도 파일로 존재하지 않습니다. 앱이 실행될 때마다 나이스 서버에 주문서를 보내고 응답을 받아 표시한 것입니다. 데이터가 "가져다 두는 것"에서 "흘러오는 것"으로 바뀌는 순간입니다. 내일 이 페이지를 열면, 아무것도 고치지 않아도 내일 식단이 나옵니다.

4. 관찰 — 표에 없던 것이 API엔 있다

급식실 앞에 붙은 식단표에는 메뉴 이름이 전부입니다. 그런데 API 응답에는 메뉴마다 알레르기 유발 식품 번호가 붙어 있고, 한 끼의 칼로리와 재료의 원산지까지 들어 있습니다. 같은 급식인데, 어떤 창구로 받느냐에 따라 손에 들어오는 속성이 다릅니다. 교과서 21~22쪽에서 "문제 상황에 따라 중요한 속성이 달라진다"고 배웠습니다 — 알레르기가 있는 학생에게는 식단표에 없던 이 번호들이 가장 중요한 속성일 수 있습니다.

규모도 가늠해 봅시다. 최근 1년치(2025-09-01~2026-07-15)를 모으면 총 199건 — 중식 154일과 석식 45일 — 이고, 등장한 고유 메뉴는 453종, 하루 평균 6.8품입니다. 이렇게 모은 한 학기치 데이터는 13차시에 "제육볶음이 나오는 날, 국은 무엇이 나올까"라는 질문으로 다시 만납니다.

제출할 "한 줄 관찰"은 다음 중 하나를 골라 자기 말로 쓰면 됩니다.

  • 식단표에는 없는데 API 응답에는 있는 정보 하나와, 그 정보가 유용한 사람은 누구인가.
  • 같은 급식 데이터인데 창구(식단표/API)에 따라 속성이 달라지는 까닭은 무엇이라 생각하는가.
  • 급식이 없는 날의 응답을 보고 알게 된 것 한 가지.
📮 오늘의 제출

클래스룸 과제로 내 앱의 급식 페이지 스크린샷 + 한 줄 관찰(식단표에 없는데 API에는 있는 정보 하나)을 제출합니다. 오늘은 별도 폼이 없습니다 — 2차시 폼 Ⅰ-02c에서 다룬 반정형 개념을 실전으로 회수하는 날입니다.

5. 개념 정리 — 인증키는 왜 필요한가

오늘 배운 것을 한 줄로 줄이면 이렇습니다. API는 데이터를 주문하는 창구이고, 응답으로 오는 JSON은 표로 변환해 쓰는 반정형 데이터다. 내려받은 CSV가 "그 시점의 복사본"이라면 API 호출은 "지금의 데이터"이며, 조건을 지정해 필요한 만큼만 받습니다. 2차시에 머리로 구분했던 정형·반정형이 오늘 손끝에서 구분되었습니다.

마지막으로 인증키입니다. 창구가 아무에게나 무제한으로 열려 있으면 서버는 감당할 수 없고, 문제가 생겨도 누구의 호출인지 알 수 없습니다. 인증키는 사용량을 관리하고 책임 소재를 밝히는 장치입니다. 그래서 키는 나를 증명하는 값이고, 코드에 적어 공개 저장소에 올리는 순간 남이 내 이름으로 주문할 수 있게 됩니다. 키를 코드가 아니라 비밀값 보관함에 넣는 오늘의 습관은, 14차시 데이터 윤리에서 다시 이야기할 주제의 첫 연습입니다.

6. 확인 문제

문제 1 — 내려받은 CSV 파일과 API 호출의 차이를 두 가지 쓰시오.

예시 답안 — ① 최신성: CSV는 내려받은 시점의 복사본이라 이후 변경이 반영되지 않지만, API는 호출할 때마다 서버의 최신 데이터를 받는다. ② 선택 조회: CSV는 제공자가 묶어 둔 파일 전체를 받지만, API는 날짜·학교 같은 조건을 지정해 필요한 부분만 받을 수 있다.

문제 2 — 급식 API의 JSON 응답은 정형·반정형·비정형 중 무엇이며, 그 근거는 무엇인가?

예시 답안 — 반정형 데이터다. 이름표와 값의 쌍으로 구조가 존재하지만, 표처럼 행과 열이 고정되어 있지는 않고 구조를 바꿀 수도 있는 유연한 형태이기 때문이다. 교과서의 정의대로 "일부분이 정형화된 데이터"이며, 필요하면 표 형태로 변환해 분석에 쓸 수 있다.

문제 3 — 인증키를 코드에 직접 쓰지 않고 비밀값 보관함(secrets)에 넣는 이유는 무엇인가?

예시 답안 — 인증키는 사용량 관리와 책임 소재를 위해 나에게 발급된 값이다. 코드에 쓴 채 공개 저장소에 올리면 누구나 내 키로 API를 호출할 수 있어, 사용량 한도를 잃거나 내 이름으로 문제가 생길 수 있다. 비밀값 보관함에 넣으면 코드는 공개해도 키는 공개되지 않는다.

🎒 오늘의 체크

  • API를 식당의 메뉴판·주문서·서빙에 비유해 설명할 수 있다.
  • 주소창에서 급식 API의 JSON 원문을 확인하고, 이름표-값 구조를 찾았다.
  • 날짜를 고르면 그날 식단이 나오는 급식 페이지를 내 앱에 추가했다.
  • 인증키를 비밀값 보관함에 넣었고, 그 이유를 말할 수 있다.
