데이터베이스와 수파베이스 — 교사 진행안

학생용 13차시 페이지 ↗를 화면에 띄운 채 진행합니다. 여기에는 시간표 · 멘트 · 예상 질문 · 예상 오류 · 이론 심화를 덧댔습니다. 이번 차시는 사전 준비가 절반입니다 — 수파베이스 연습용 프로젝트와 대결 기록 표(menu_duels)를 교사가 미리 만들어 두고, 학생은 수업에서 그 표에 연결하거나 배포된 앱 주소를 엽니다. 아래 준비 체크를 수업 전날까지 마치세요.

🔧 수업 전 준비 체크 (필수 · 전날까지)
  • 연습용 수파베이스 프로젝트를 B반·E반 따로 하나씩(총 2개) 생성하고, 대결 기록 표(표 이름 menu_duels, 열은 id·game_id·round·left_menu·right_menu·winner·created_at 일곱 개)를 아래 SQL로 미리 만들어 둔다. 학생은 표를 만들지 않고 연결만 한다. 만든 뒤 Table Editor에서 일곱 열과 RLS 활성화 상태, 0행을 눈으로 확인한다.
  • 권한 규칙(RLS)이 아래 SQL에 함께 들어 있다 — 이번 설계는 조회와 대결 기록 추가만 허용하고 수정·삭제는 열지 않는다. 학생 앱이 수정·삭제를 시도하면 데이터베이스가 막는다. 학생 안내는 "선생님이 권한 규칙을 미리 설정해 두었다"까지면 충분하다. 오류가 난다고 RLS를 끄거나 관리자 키를 넣지 않는다.
  • 접속 정보(주소·키)를 반별로 다른 값으로 각 학급 클래스룸에 비공개 게시할 준비를 한다. Connect 또는 Settings → API Keys의 Project URL과 sb_publishable_… 키를 쓴다. 학생은 이 값을 비밀 금고(Secrets)에 SUPABASE_URL·SUPABASE_KEY 두 줄로 넣는다(학생용 실습 첫 단계에 두 줄 생성기와 "이름 세 곳 일치" 표가 있음). secret·service_role 키와 DB 비밀번호는 배포하지 않는다. 공개 게시판·판서 금지(2차시의 비밀 금고 원칙 그대로).
  • 후보 여덟 가지가 글자까지 일치하는지 확인한다 — 아래 SQL의 CHECK 목록과 학생용 ① 프롬프트의 후보(제육볶음·간장찜닭·가자미순살튀김·돈육불백·미트볼데리야끼볶음·수육·진미채고추장볶음·치즈떡닭갈비)가 한 글자라도 다르면 저장이 거부된다. 후보는 12차시 급식 184일 집계에서 주요리만 골라 고정한 목록이다.
  • 교과서 31쪽 쇼핑몰 테이블 설계(Ⅰ-03b)를 실물로 보여 줄 수파베이스 테이블 화면을 열어 둔다. 속성 이름·데이터형·조건이 설계표 그대로 나타난다.
  • 교사 예비 앱을 하나 배포해 둔다 — 도입 시연용이자, 배포가 막힌 모둠의 구제용이다. 기본 실습은 모둠별 앱 하나이므로 모둠에서 한 명이 배포하고 나머지는 그 주소를 열어 참여하면 된다.
  • 반별 프로젝트 운영 규칙(2026-09-03 교사 결정) — 프로젝트 이름에 반을 넣어 구분하고(예: ds-2026-B, ds-2026-E), 두 프로젝트 모두 같은 표 이름 menu_duels·같은 열 구성·같은 권한 규칙으로 만든다. 그래야 학생용 ① 프롬프트와 예시 코드를 두 반이 그대로 쓴다. 게시글을 다른 반에 잘못 올리면 그 반의 대결 기록이 남의 반 표에 섞이므로, 게시 전에 반 이름과 주소의 짝을 한 번 더 확인한다. 키를 재발급할 일이 생기면 해당 반만 바꾸면 된다.
  • 팀 구성 방식과 주제 카드 양식을 정해 둔다 — 팀 구성을 중간고사 이후로 이월할지 여부도 학급 사정을 보고 미리 판단.
🗄️ 수파베이스 프로젝트 설정 SQL — 대결 기록 표 + 권한 규칙 (반별 프로젝트마다 한 번, 복사해서 SQL Editor에 붙여 넣기)

대시보드의 SQL Editor → New query에 아래 전체를 붙여 넣고 Run을 누른다. B반·E반 프로젝트에 각각 한 번씩 실행한다. 표 이름·열·권한이 두 반에서 같아야 학생용 프롬프트와 예시 코드를 그대로 쓴다. 학생용 3절 'SQL · 표 만들기'와 같은 내용이며, 뒤에 교사용 운영 메모만 덧붙였다. 표 만들기 부분이 학생용 3절 설계표(속성명·데이터형·조건)의 실행본이다. 이미 표가 있다는 오류가 나면 반복 실행하거나 기존 표를 지우지 말고, 올바른 프로젝트를 열었는지부터 확인한다.

수파베이스_반찬월드컵_설정.sql
-- =====================================================================
-- 13차시 반찬 월드컵 대결 기록 표 — 수파베이스 프로젝트 설정 SQL
-- 실행 위치: 수파베이스 대시보드 → SQL Editor → New query → 전체 붙여 넣기 → Run
-- 두 반(B·E) 프로젝트 모두 이 파일을 그대로 실행한다. 표 이름·열·권한이 같아야
-- 학생용 ① 프롬프트와 예시 코드를 두 반이 그대로 쓴다.
-- =====================================================================

CREATE TABLE public.menu_duels (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  game_id text NOT NULL CHECK (length(btrim(game_id)) > 0),
  round text NOT NULL CHECK (round IN ('8강', '4강', '결승')),
  left_menu text NOT NULL CHECK (left_menu IN ('제육볶음', '간장찜닭', '가자미순살튀김', '돈육불백', '미트볼데리야끼볶음', '수육', '진미채고추장볶음', '치즈떡닭갈비')),
  right_menu text NOT NULL CHECK (right_menu IN ('제육볶음', '간장찜닭', '가자미순살튀김', '돈육불백', '미트볼데리야끼볶음', '수육', '진미채고추장볶음', '치즈떡닭갈비')),
  winner text NOT NULL,
  CHECK (left_menu <> right_menu),
  CHECK (winner IN (left_menu, right_menu)),
  created_at timestamptz NOT NULL DEFAULT now()
);
ALTER TABLE public.menu_duels ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON public.menu_duels FROM anon, authenticated;
GRANT USAGE ON SCHEMA public TO anon;
GRANT SELECT ON public.menu_duels TO anon;
GRANT INSERT (game_id, round, left_menu, right_menu, winner) ON public.menu_duels TO anon;
GRANT USAGE ON SEQUENCE public.menu_duels_id_seq TO anon;
CREATE POLICY "read_practice_votes" ON public.menu_duels
  FOR SELECT TO anon USING (true);
CREATE POLICY "insert_practice_votes" ON public.menu_duels
  FOR INSERT TO anon WITH CHECK (true);

학생용 13차시 3절의 'SQL · 표 만들기' 코드와 같은 내용이므로, 학생이 그 코드를 읽으면 자기 앱이 연결하는 표의 설계를 그대로 보게 된다. 접속 정보(Project URL·publishable 키)는 Connect 또는 Settings → API Keys에서 복사해 반별 클래스룸에 비공개 게시하고, secret·service_role 키는 배포하지 않는다.

🎙️ 시간이 밀리면 — 무른 경계는 팀 구성 쪽

시간이 밀려도 반드시 다루어야 할 것은 수파베이스 실습입니다. 모둠마다 월드컵 앱이 돌아가고, 서로 다른 기기의 대결 기록이 한 표에 쌓이는 것까지 확인한다. 팀 구성(32~45′)은 중간고사 이후 프로젝트 첫 시간으로 통째로 이월해도 된다(설계상 무른 경계). 이월한다면 그 시간을 ③ 승률 분석과 3절 SQL 읽기(문장 조립기·시뮬레이터)로 채우고, 주제 카드 양식만 미리 나눠 주어 시험 기간에 생각해 오게 한다. 갤러리 최종 관람도 이월 1순위이다.

블록별 진행 노트

DB의 필요 (0~10′)

🎙️ 멘트 — 질문 하나로 시작한다

“지금까지 만든 앱은 데이터를 읽기만 했어요. 오늘은 데이터를 만들어 모읍니다 — 친구들이 가장 좋아하는 반찬을 반찬 월드컵으로 가려 보는 거예요. 그런데 여러분 서른 명이 각자 기기에서 고른 결과를, CSV 파일 하나로 모을 수 있을까요?” 학생용의 클릭 그림(A와 B가 동시에 쓰는 3단계)을 전체 화면으로 함께 클릭하며 “나중에 저장한 쪽이 파일을 통째로 덮는다”를 확인한다. 이어서 모둠 과제 경험을 역추적한다(Ⅰ-03a) — “모둠 발표 자료를 파일로 주고받다가 겪은 일 있죠? 최신본이 뭔지 헷갈리고, 누가 고친 게 사라지고.” 그다음 미리 열어 둔 수파베이스 화면으로 교과서 31쪽 쇼핑몰 설계를 실물 확인한다 — “교과서의 설계표가 진짜 서비스에서는 이렇게 생겼습니다.” 마지막으로 오늘의 반전을 예고만 해 둔다: “사실 여러분은 이 도구를 이미 한 학기 내내 썼습니다. 정리 시간에 밝힙니다.”

🙋 예상 질문

“구글 시트도 여럿이 동시에 쓰는데, 그것도 데이터베이스예요?” → “좋은 관찰입니다. 동시 편집 문제를 풀어 준다는 점에서 같은 방향의 도구입니다. 데이터베이스는 거기에 더해 조건 검색, 잘못된 값 차단, 사용자별 권한까지 갖춘 것 — 오늘 실습에서 그 차이를 만난다.” · “내 프로젝트를 따로 만들면 안 돼요?” → “팀 프로젝트에서는 팀별로 만들 수 있다. 오늘은 여러 기기의 기록이 한곳에 모이는 것을 확인하는 날이라, 모둠이 같은 표를 쓴다. 각자 앱을 만들어도 좋지만 접속 정보는 같은 프로젝트의 것을 써야 기록이 합쳐진다.”

①②③ 실습 — 반찬 월드컵 (10~32′)

🎙️ 운영 — 두 기기의 기록이 한 표에 모이는 것이 오늘의 발견

접속 정보를 클래스룸 비공개 게시로 전달한다. 기본 실습은 모둠별 앱 하나다 — 모둠에서 한 명이 ①을 붙여 받은 코드를 main.py로 저장하고 requirements.txt(streamlit·supabase·pandas·plotly)와 함께 올려 배포하며, 비밀 금고에 두 줄을 넣는 것까지 확인한다. 나머지는 배포된 앱 주소를 열어 참여한다. 앱이 돌아가면 한 판을 끝까지 하게 한다 — 8강 네 번, 4강 두 번, 결승 한 번으로 일곱 번을 고르면 우승 반찬이 나오고 표에 일곱 행이 쌓인다. 이어서 서로 다른 두 기기에서 한 판씩 마치고 "결과 새로 불러오기"를 눌러 대결 기록 수가 14 늘었는지 확인하는 것이 이 차시의 발견이다. “다른 기기에서 고른 결과가 내 화면에도 보이죠? 여러분 데이터가 방금 ‘내 파일’에서 ‘우리의 저장소’가 됐습니다.” ③(학급 승률 분석)까지 간 학생에게는 승리 수와 승률을 함께 읽는 이유를 물어 준다 — 이긴 반찬만 다음 라운드에 올라가므로 반찬마다 겨룬 횟수가 다르고, 분모가 다른 값을 그대로 견주면 안 된다는 것이 오늘의 판단이다. 저장 확인 안내가 뜬 학생에게는 반복 제출 대신 판 번호로 최근 기록을 확인하게 한다.

🧯 예상 오류

AI가 접속 정보를 코드에 직접 적으라고 안내함 → ①의 “접속 정보는 비밀 금고의 SUPABASE_URL과 SUPABASE_KEY에서 읽어 줘” 줄이 빠졌는지 확인하고, 코드에 주소·키가 박혀 있으면 2차시의 비밀 금고 원칙 그대로 옮긴다. 다음 시간 데이터 윤리에서 이 장면을 다시 점검한다. · 수파베이스 라이브러리를 못 찾는 오류 → requirements.txt에 supabase가 없는 것이다. “필요한 라이브러리를 requirements.txt에 추가해 줘”로 잇게 한다. · 연결은 됐는데 저장이 안 됨 → (가)AI가 표 이름을 새로 지어냈거나(학생은 표를 만들 수 없다) (나)후보 이름이 한 글자 다르거나 (다)수정·삭제를 시도한 경우다. 표 이름 menu_duels와 다섯 열(game_id·round·left_menu·right_menu·winner), 후보 여덟 가지의 철자를 프롬프트에서 확인하게 한다. 이 표는 조회와 추가만 허용하므로 수정·삭제 기능을 넣으면 거부된다. · 같은 두 반찬을 넣거나 승자가 둘 중 하나가 아님 → 데이터베이스의 CHECK 조건이 막는다. 오류가 아니라 설계대로 동작한 것이고, 교과서 26쪽의 무결성이 실제로 일하는 장면이다. · 접속 정보 오타 → 붙여넣을 때 앞뒤 공백이나 따옴표가 섞인 경우가 흔하다. 직접 타이핑 금지, 복사만. · 내 대결 기록이 남의 앱에도 보인다는 항의 → 고장이 아니라 정상이다. 같은 표를 공유하므로 모든 앱에 같은 기록이 보인다 — “그게 바로 ‘여러 사람이 공유하여 사용하는 데이터의 집합’(교과서 26쪽)이다.” · 오류를 없애려고 RLS를 끄거나 관리자 키를 넣음 → 금지한다. 필요한 동작만 교사와 확인한다.

📖 이론 심화 — 네 동작과 권한, 그리고 RLS (교사만)

데이터베이스가 하는 일은 결국 네 동작 — 생성·읽기·갱신·삭제(교과서 29쪽, CRUD)이다. 오늘 학생 앱에 열려 있는 것은 생성과 읽기 둘뿐이고, 갱신과 삭제는 3절 SQL 읽기 자료에서 문장으로만 만난다. 이 절제 자체가 오늘의 교육 내용이다 — 아무나 남의 기록을 고치거나 지울 수 있으면 안 되기 때문이다. 실제 서비스는 이 권한 규칙을 앱이 아니라 데이터베이스 쪽에 세워 두며, 수파베이스에서는 그 장치가 행 단위 보안(RLS)이다. 준비 SQL의 REVOKE ALL 뒤에 GRANT SELECT와 다섯 열짜리 GRANT INSERT만 다시 준 것, 그리고 조회·추가 정책 두 개만 만든 것이 그 구현이다. 학생에게는 “선생님이 허용할 동작만 미리 정해 뒀다”까지면 충분하고, 학생용 3절의 ‘권한 정책’ 절이 같은 내용을 읽기 자료로 다룬다. 덧붙여 이 설계는 1인 1표를 보장하지 않는다 — 로그인이 없으므로 같은 사람이 여러 판을 할 수 있고, 그래서 대결 기록 수는 참여 인원이 아니다.

팀 구성·주제 (32~45′)

🎙️ 운영 — 주제 카드는 세 물음으로

팀(2~3인)은 관심 질문이 비슷한 사람끼리 묶는 것이 기본이다. 팀이 서면 주제 카드를 작성한다 — ①팀의 질문 ②맞는 분석 틀(회귀·분류·군집·연관 중) ③데이터 후보 3개. 각 후보는 세 물음으로 판단하게 한다(교과서 176쪽 탐구활동, Ⅳ-01b): 데이터가 충분히 있는가 · 문제 해결에 적합한가 · 법적·윤리적으로 올바른가. 세 번째 물음은 오늘 판정하지 않고, 다음 시간(14차시 데이터 윤리)에 세울 점검 목록(개인정보·출처·약관·편향)으로 다시 걸러 낸다고 예고하면 두 차시가 이어진다. 주제 카드는 오늘 확정이 아니라 후보 제출이다 — “시험 끝나고 프로젝트 첫 시간에 이 카드에서 출발한다”고 안내해 부담을 낮춘다.

🙋 예상 질문

“팀 하고 싶은 사람이 없어요.” → 무리해서 오늘 정하지 않는다. 팀 구성은 프로젝트 첫 시간으로 이월할 수 있는 무른 경계이다 — 혼자 주제 카드를 써 내게 하고, 비슷한 질문을 낸 학생끼리 다음에 이어 주는 편이 낫다. · “데이터가 있는지 없는지 어떻게 알아요?” → “한 학기 동안 쓴 곳들부터 뒤져 보세요 — 공공데이터포털, 학교 정보 API, 영화 API처럼 문서가 공개된 곳. 데이터 확인 전에는 주제를 확정하지 않는 것, 그게 첫 물음이 존재하는 이유이다.”

3절 SQL — 읽기 자료 · 도전 (시간표 밖)

🎙️ 운영 — 50분 안에 넣지 않는다

학생용 3절(SQL)은 교과서 밖 보충이라 시간표에 넣지 않았습니다. 다만 3절 첫머리의 'SQL · 표 만들기'는 교사가 미리 실행한 준비 SQL과 같은 코드이므로, "여러분 앱이 연결한 표가 이렇게 만들어졌다"고 한 번 짚어 주면 준비와 실습이 이어집니다. 월드컵 앱이 먼저 돌아간 학생에게 "SQL 문장 조립기"를 열어 보게 하고, 나머지는 읽기 자료와 15차시 예비 시간, 시험 대비 자습으로 돌립니다. SQL 절에서 꼭 다루어야 할 것은 세 가지로 좁혀 안내합니다 — ①SQL 문장 한 줄을 읽고 네 동작 중 무엇인지 말하기 ②WHERE 없는 UPDATE·DELETE가 위험한 까닭 ③GROUP BY에서 묶은 열이 아닌 열을 그대로 쓰면 오류가 나는 까닭(영양사 선생님 이야기 장면 2). CREATE TABLE 문법과 JOIN은 읽기 자료로 둔다고 분명히 안내해 두는 편이 좋습니다. 학생용 3절의 설계표 조립기는 교과서 31쪽 탐구활동(Ⅰ-03b 폼)과 짝입니다. 폼에 자기 설계를 먼저 적게 한 뒤 조립기에 같은 설계를 넣어 SQL 문장과 우리말 해석을 읽게 하면, "조건" 칸이 SQL의 어느 낱말이 되는지 스스로 확인합니다. 이어지는 SQL 시뮬레이터(반려동물 인스타그램 게시물 표·댓글 표)는 문장을 직접 써서 FROM → WHERE → GROUP BY → SELECT → ORDER BY → LIMIT 단계를 눈으로 보는 도구입니다. "민수의 오류" 예시 단추가 GROUP BY 규칙 오류를 그대로 재현하므로, 장면 2를 설명할 때 화면에 띄우면 됩니다.

🙋 예상 질문

"SQL을 외워야 하나요?" → "아니요. AI가 짜 준 코드 속 select·insert가 무슨 뜻인지 읽을 수 있으면 됩니다. 외우는 대신 조립기로 문장이 어떻게 만들어지는지 한 번 보세요." · "수파베이스 SQL 편집기에서 직접 실행해 봐도 돼요?" → 교사가 준비한 연습용 프로젝트에서는 학생 계정에 편집기 권한이 없으므로 안 된다. 원하는 학생은 자기 개인 프로젝트를 만들어 시험하게 하되, 개인정보가 든 데이터는 넣지 않도록 14차시 기준을 미리 말해 둔다. · "파이썬 코드에는 GROUP BY가 없는데요?" → 월드컵 앱이 쓰는 라이브러리는 표를 통째로 가져온 뒤 파이썬에서 묶는다(③ 분석 화면의 반찬별 집계가 그것이다). SQL 편집기에서 직접 GROUP BY를 쓰는 것과 결과는 같고, 어느 쪽에서 세느냐만 다르다.

정리 — 다음 시간 예고 (45~50′)

🎙️ 멘트 — 갤러리의 정체 공개, 그리고 예고

도입에서 예고한 반전을 회수한다. “작품을 올리고 서로 피드백을 남긴 우리 갤러리 — 그게 바로 수파베이스입니다. 여러분은 오늘 처음 배운 게 아니라, 한 학기 내내 쓰던 도구의 이름을 오늘 알게 된 것입니다.” 이어서 다음 시간을 예고한다. “오늘 팀과 데이터 후보를 정했습니다. 다음 시간에는 한 학기의 실습 전체를 윤리의 기준으로 점검하고, 그 기준으로 후보를 걸러 주제 카드를 확정합니다.” 공통 수업 전체의 매듭은 다음 시간(데이터 윤리)에서 짓는다.

🧾 생기부 관찰 지점

질문 설정 — 주제 카드에서 관심사를 "데이터로 답할 수 있는 형태"의 질문으로 스스로 고쳐 쓴 학생(예: "게임이 좋다" → "장르별 이용 시간 데이터로 무엇을 예측할 수 있나"). · 한계 인식 — 데이터 후보를 세 물음, 특히 윤리 관문으로 스스로 걸러 내고 그 이유를 적은 팀. · 개념 연결 — 두 기기의 기록이 한 표에 모이는 장면이나 CSV의 세 벽을 자기 모둠 경험과 연결해 설명한 학생, 승리 수와 승률의 분모 차이를 8차시 R²·12차시 향상도의 "비교 기준" 습관과 스스로 이어 말한 학생. 주제 카드는 프로젝트 세특의 출발 기록이 되므로 전량 수합·보관하세요.

✅ 13차시 마무리 체크 (교사)

  • 모둠마다 월드컵 앱이 작동하는가? (한 판 일곱 번 완주 + 우승 반찬 — 막힌 모둠은 교사 예비 앱으로 구제)
  • 서로 다른 두 기기에서 한 판씩 마쳐 대결 기록이 14 늘었는지 확인했는가? (판별 8강 4행·4강 2행·결승 1행)
  • 접속 정보가 코드가 아니라 비밀 금고에 있는지 확인했는가? (14차시 윤리 점검의 예고)
  • 승리 수와 승률을 함께 읽어야 하는 이유(반찬마다 겨룬 횟수가 다름)를 학생의 말로 들었는가?
  • 팀 구성·주제 카드를 마쳤는가, 또는 이월을 공지했는가? (카드 수합·보관)
  • 갤러리가 수파베이스라는 안내와 다음 시간(데이터 윤리) 예고를 남겼는가?
  • SQL 절의 핵심 세 가지(문장 읽기 · WHERE 없는 갱신·삭제 · GROUP BY 오류의 까닭)를 안내했는가?
  • 프로젝트 첫 시간 안내(카드에서 출발)를 공지했는가?
