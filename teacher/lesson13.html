데이터베이스와 수파베이스 — 교사 진행안

학생용 13차시 페이지 ↗를 화면에 띄운 채 진행합니다. 여기에는 시간표 · 멘트 · 예상 질문 · 예상 오류 · 이론 심화를 덧댔습니다. 이번 차시는 사전 준비가 절반입니다 — 수파베이스 학급 공용 프로젝트를 교사가 미리 만들어 두고, 학생은 수업에서 연결만 합니다. 아래 준비 체크를 수업 전날까지 마치세요.

🔧 수업 전 준비 체크 (필수 · 전날까지)
  • 학급별 수파베이스 프로젝트를 B반·E반 따로 하나씩(총 2개) 생성하고, 방명록 테이블(표 이름 guestbook, 열은 id·name·message·created_at·password)을 미리 만들어 둔다 — 마지막 열은 도전 과제(갱신·삭제)에서 쓴다 — 학생은 테이블을 만들지 않고 연결만 한다.
  • 권한 규칙(RLS)을 테이블에 설정해 둔다 — 누구나 쓰고 읽을 수 있되 함부로 지우지 못하는 성격의 규칙. 학생 안내는 "선생님이 권한 규칙을 미리 설정해 두었다"까지면 충분하다.
  • 접속 정보(주소·키)를 반별로 다른 값으로 각 학급 클래스룸에 비공개 게시할 준비 — 학생이 받아서 비밀 금고(Secrets)에 SUPABASE_URL·SUPABASE_KEY 두 줄로 넣는다(학생용 실습 첫 단계에 두 줄 예시와 "이름 세 곳 일치" 표가 있음). 게시글에도 두 줄을 그 이름 그대로 적어 보내면 학생은 값만 바꿔 붙인다. 공개 게시판·판서 금지(2차시의 비밀 금고 원칙 그대로).
  • 교과서 31쪽 쇼핑몰 테이블 설계(Ⅰ-03b)를 실물로 보여 줄 수파베이스 테이블 화면을 열어 둔다 — 속성 이름·데이터형·조건이 설계표 그대로 나타나는 장면.
  • 교사 예비 방명록 앱을 하나 배포해 둔다 — 막힌 학생의 구제용이자, 도입 시연용.
  • 반별 프로젝트 운영 규칙(2026-09-03 교사 결정) — 프로젝트 이름에 반을 넣어 구분하고(예: ds-2026-B, ds-2026-E), 두 프로젝트 모두 같은 표 이름 guestbook·같은 열 구성·같은 권한 규칙으로 만든다. 그래야 학생용 ① 프롬프트와 예시 코드를 두 반이 그대로 쓴다. 게시글을 다른 반에 잘못 올리면 그 반 학생의 글이 남의 반 방명록에 쌓이므로, 게시 전에 반 이름과 주소의 짝을 한 번 더 확인한다. 키를 재발급할 일이 생기면 해당 반만 바꾸면 된다.
  • 팀 구성 방식과 주제 카드 양식을 정해 둔다 — 팀 구성을 중간고사 이후로 이월할지 여부도 학급 사정을 보고 미리 판단.
🗄️ 수파베이스 프로젝트 설정 SQL — 표 + 권한 규칙 (반별 프로젝트마다 한 번, 복사해서 SQL Editor에 붙여 넣기)

대시보드의 SQL Editor → New query에 아래 전체를 붙여 넣고 Run을 누릅니다. 마지막 조회의 결과 표가 뜨면 성공입니다. B반·E반 프로젝트에 각각 한 번씩 실행합니다. 표 이름·열·권한이 두 반에서 같아야 학생용 프롬프트와 예시 코드를 그대로 씁니다. 학생용 3절의 설계표·CREATE TABLE 예문과 같은 구조이고, 갱신은 message 열만 열어 두어 이름·비밀번호·시각은 바꿀 수 없습니다. 비밀번호 확인은 학생 앱 안에서 하는 검사입니다(교재 서술과 일치).

수파베이스_방명록_설정.sql
-- =====================================================================
-- 13차시 방명록 표 — 수파베이스 프로젝트 설정 SQL (반별 프로젝트마다 한 번 실행)
-- 실행 위치: 수파베이스 대시보드 → SQL Editor → New query → 전체 붙여 넣기 → Run
-- 두 반(B·E) 프로젝트 모두 이 파일을 그대로 실행한다. 표 이름·열·권한이 같아야
-- 학생용 ① 프롬프트와 예시 코드를 두 반이 그대로 쓴다.
-- =====================================================================

-- 1) 표 만들기 — 학생용 교재 3절의 설계표(속성명·데이터형·조건)와 같은 구조
create table if not exists public.guestbook (
  id          bigint generated always as identity primary key,          -- 정수 · 자동 증가 · 기본 키
  name        text not null check (char_length(btrim(name)) between 1 and 20),      -- 비워 둘 수 없음, 20자 이내
  message     text not null check (char_length(btrim(message)) between 1 and 200),  -- 비워 둘 수 없음, 200자 이내
  password    text check (coalesce(password, '') ~ '^([0-9]{4})?$'),   -- 비우거나 숫자 네 자리
  created_at  timestamptz not null default now()                        -- 저장 시각 자동
);

-- 2) 권한 규칙 켜기 — 켜는 순간 정책으로 허용한 동작만 통과한다
alter table public.guestbook enable row level security;

-- 3) 정책 — 학생 앱은 공개용(anon) 키로 접속한다. 네 동작을 모두 열되 범위를 좁힌다.
drop policy if exists guestbook_select on public.guestbook;
drop policy if exists guestbook_insert on public.guestbook;
drop policy if exists guestbook_update on public.guestbook;
drop policy if exists guestbook_delete on public.guestbook;

create policy guestbook_select on public.guestbook
  for select to anon, authenticated using (true);                       -- 읽기: 누구나

create policy guestbook_insert on public.guestbook
  for insert to anon, authenticated with check (true);                  -- 생성: 누구나 (빈 값은 위 check 제약이 막음)

create policy guestbook_update on public.guestbook
  for update to anon, authenticated using (true) with check (true);     -- 갱신: 도전 과제용 (비밀번호 확인은 앱에서)

create policy guestbook_delete on public.guestbook
  for delete to anon, authenticated using (true);                       -- 삭제: 도전 과제용

-- 4) 열 단위 권한 — 갱신은 message 열만 허용 (이름·비밀번호·작성 시각은 바꿀 수 없게)
revoke update on public.guestbook from anon, authenticated;
grant  update (message) on public.guestbook to anon, authenticated;

-- 5) 확인용 조회 (Run 뒤 결과 표가 뜨면 성공)
select id, name, message, created_at from public.guestbook order by created_at desc limit 5;

-- ---------------------------------------------------------------------
-- 운영 메모
-- · 접속 정보: Project Settings → API 의 Project URL 과 anon public 키를 학생용 두 줄
--   (SUPABASE_URL, SUPABASE_KEY)로 각 반 클래스룸에 비공개 게시한다. service_role 키는 절대 배포하지 않는다.
-- · 시연용 첫 글:  insert into public.guestbook (name, message, password) values ('선생님', '첫 글입니다', '0000');
-- · 학기 중 초기화(전부 지우기):  truncate table public.guestbook restart identity;
-- · 키 유출 의심 시: Project Settings → API → anon 키 재발급(rotate) 후 학생 Secrets 값만 교체.
-- · 학기말: 표를 남길지 지울지 결정.  drop table public.guestbook;  (지우면 복구 불가)
-- ---------------------------------------------------------------------

같은 내용이 저장소의 curriculum/수파베이스_방명록_설정.sql에 있습니다. 접속 정보(Project URL·anon 키)는 Project Settings → API에서 복사해 반별 클래스룸에 비공개 게시하고, service_role 키는 절대 배포하지 않습니다.

🎙️ 시간이 밀리면 — 무른 경계는 팀 구성 쪽

오늘 반드시 남길 것은 수파베이스 실습입니다 — 전원의 앱에 방명록이 붙고 글이 쌓이는 것까지. 팀 구성(32~45′)은 중간고사 이후 프로젝트 첫 시간으로 통째로 이월해도 됩니다(설계상 무른 경계). 이월한다면 그 시간을 도전 과제(고치기·지우기 + 비밀번호)로 채우고, 주제 카드 양식만 미리 나눠 주어 시험 기간에 생각해 오게 하세요. 갤러리 최종 관람도 이월 1순위입니다.

블록별 진행 노트

DB의 필요 (0~10′)

🎙️ 멘트 — 소원 하나로 시작한다

“여러분 앱은 한 학기 동안 데이터를 읽기만 했어요. 오늘 소원 하나를 이룹니다 — 내 앱에 방문 소감 받기. CSV 파일로 될까요?” 학생용의 클릭 그림(A와 B가 동시에 쓰는 3단계)을 전체 화면으로 함께 클릭하며 “나중에 저장한 쪽이 파일을 통째로 덮는다”를 확인합니다. 이어서 모둠 과제 경험을 역추적합니다(Ⅰ-03a) — “모둠 발표 자료를 파일로 주고받다가 겪은 일 있죠? 최신본이 뭔지 헷갈리고, 누가 고친 게 사라지고.” 그다음 미리 열어 둔 수파베이스 화면으로 교과서 31쪽 쇼핑몰 설계를 실물 확인합니다 — “교과서의 설계표가 진짜 서비스에서는 이렇게 생겼습니다.” 마지막으로 오늘의 반전을 예고만 해 둡니다: “사실 여러분은 이 도구를 이미 한 학기 내내 썼습니다. 정리 시간에 밝힙니다.”

🙋 예상 질문

“구글 시트도 여럿이 동시에 쓰는데, 그것도 데이터베이스예요?” → “좋은 관찰이에요. 동시 편집 문제를 풀어 준다는 점에서 같은 방향의 도구입니다. 데이터베이스는 거기에 더해 조건 검색, 잘못된 값 차단, 사용자별 권한까지 갖춘 것 — 오늘 실습에서 그 차이를 만납니다.” · “내 프로젝트를 따로 만들면 안 돼요?” → “팀 프로젝트에서는 팀별로 만들 수 있어요. 오늘은 연결하는 법을 익히는 날이라 학급 공용으로 갑니다.”

①②③ 실습 — 방명록 (10~32′)

🎙️ 운영 — 동시성 확인이 오늘의 발견

접속 정보를 클래스룸 비공개 게시로 전달하고, 비밀 금고에 넣는 것까지 확인한 뒤 ①을 붙이게 합니다. 앱이 돌아가면 반드시 옆 친구의 앱에 서로 글을 남기게 하세요 — 두 사람이 거의 동시에 써도 기록이 덮이지 않고 각각 한 행으로 쌓이는 것을 서로의 화면에서 확인하는 순간이 이 차시의 발견입니다. “새로고침해 보세요. 친구 컴퓨터에서도 보이죠? 여러분 데이터가 방금 ‘내 파일’에서 ‘우리의 저장소’가 됐습니다.” ③(빈 칸 차단)까지 마친 학생에게는 “방금 여러분이 교과서 26쪽의 데이터 무결성을 직접 구현한 겁니다”라고 이름을 붙여 주고, 빠른 학생은 도전 과제(고치기·지우기 + 네 자리 비밀번호)로 보냅니다.

🧯 예상 오류

AI가 접속 정보를 코드에 직접 적으라고 안내함 → ①의 “접속 정보는 비밀 금고(secrets)의 SUPABASE_URL과 SUPABASE_KEY에서 불러와” 줄이 빠졌는지 확인하고, 코드에 주소·키가 박혀 있으면 2차시의 비밀 금고 원칙 그대로 옮기게 합니다. 다음 시간 데이터 윤리에서 이 장면을 다시 점검합니다. · 수파베이스 라이브러리를 못 찾는 오류 → requirements.txt에 수파베이스 라이브러리가 없는 것입니다. “필요한 라이브러리를 requirements.txt에 추가해 줘”로 잇게 합니다. · 연결은 됐는데 저장이 안 됨 → AI가 테이블 이름을 새로 지어냈을 가능성이 큽니다(학급 공용 프로젝트에서는 학생이 테이블을 만들 수 없음). 선생님이 만든 방명록 테이블의 정확한 이름과 열 이름을 프롬프트에 알려 주고 다시 부탁하게 합니다. · 접속 정보 오타 → 붙여넣을 때 앞뒤 공백이나 따옴표가 섞인 경우가 흔합니다. 직접 타이핑 금지, 복사만. · 내 글이 남의 앱에도 보인다는 항의 → 고장이 아니라 정상입니다. 학급 전원이 같은 테이블을 공유하므로 모든 앱에 같은 방명록이 보입니다 — “그게 바로 ‘여러 사람이 공유하여 사용하는 데이터의 집합’(교과서 26쪽)입니다.”

📖 이론 심화 — 네 동작과 권한, 그리고 RLS (교사만)

데이터베이스가 하는 일은 결국 네 동작 — 생성·읽기·갱신·삭제(교과서 29쪽)입니다. 기본 실습이 생성과 읽기, 도전 과제가 갱신과 삭제인데, 뒤의 둘에서 처음으로 권한 문제가 나타납니다 — 아무나 남의 글을 지울 수 있으면 안 되니까요. 실제 서비스는 이 권한 규칙을 앱이 아니라 데이터베이스 쪽에 세워 두며, 수파베이스에서는 그 장치가 행 단위 보안(RLS)입니다. 학급 공용 프로젝트와 우리 갤러리에 걸려 있는 규칙이 바로 이것입니다 — 학생에게는 “선생님이 같은 성격의 규칙을 미리 설정해 뒀다”까지만 말하면 되고, 도전 과제의 네 자리 비밀번호가 같은 문제의식의 간이 구현이라는 연결만 잡아 주면 충분합니다.

팀 구성·주제 (32~45′)

🎙️ 운영 — 주제 카드는 세 물음으로

팀(2~3인)은 관심 질문이 비슷한 사람끼리 묶는 것이 기본입니다. 팀이 서면 주제 카드를 작성합니다 — ①팀의 질문 ②맞는 분석 틀(회귀·분류·군집·연관 중) ③데이터 후보 3개. 각 후보는 세 물음으로 판단하게 합니다(교과서 176쪽 탐구활동, Ⅳ-01b): 데이터가 충분히 있는가 · 문제 해결에 적합한가 · 법적·윤리적으로 올바른가. 세 번째 물음은 오늘 판정하지 않고, 다음 시간(14차시 데이터 윤리)에 세울 점검 목록(개인정보·출처·약관·편향)으로 다시 걸러 낸다고 예고하면 두 차시가 이어집니다. 주제 카드는 오늘 확정이 아니라 후보 제출입니다 — “시험 끝나고 프로젝트 첫 시간에 이 카드에서 출발한다”고 안내해 부담을 낮추세요.

🙋 예상 질문

“팀 하고 싶은 사람이 없어요.” → 무리해서 오늘 정하지 않습니다. 팀 구성은 프로젝트 첫 시간으로 이월할 수 있는 무른 경계입니다 — 혼자 주제 카드를 써 내게 하고, 비슷한 질문을 낸 학생끼리 다음에 이어 주는 편이 낫습니다. · “데이터가 있는지 없는지 어떻게 알아요?” → “한 학기 동안 쓴 곳들부터 뒤져 보세요 — 공공데이터포털, 학교 정보 API, 영화 API처럼 문서가 공개된 곳. 데이터 확인 전에는 주제를 확정하지 않는 것, 그게 첫 물음이 존재하는 이유입니다.”

3절 SQL — 읽기 자료 · 도전 (시간표 밖)

🎙️ 운영 — 50분 안에 넣지 않는다

학생용 3절(SQL)은 교과서 밖 보충이라 시간표에 넣지 않았습니다. 방명록이 먼저 돌아간 학생에게 "SQL 문장 조립기"를 열어 보게 하고, 나머지는 읽기 자료와 15차시 예비 시간, 시험 대비 자습으로 돌립니다. 지필에서 묻는 범위는 세 가지로 좁혀 안내합니다 — ①SQL 문장 한 줄을 읽고 네 동작 중 무엇인지 말하기 ②WHERE 없는 UPDATE·DELETE가 위험한 까닭 ③GROUP BY에서 묶은 열이 아닌 열을 그대로 쓰면 오류가 나는 까닭(영양사 선생님 이야기 장면 2). CREATE TABLE 문법과 JOIN은 읽기 자료이며 출제하지 않는다고 분명히 안내해 두는 편이 좋습니다. 학생용 3절의 설계표 조립기는 교과서 31쪽 탐구활동(Ⅰ-03b 폼)과 짝입니다. 폼에 자기 설계를 먼저 적게 한 뒤 조립기에 같은 설계를 넣어 SQL 문장과 우리말 해석을 읽게 하면, "조건" 칸이 SQL의 어느 낱말이 되는지 스스로 확인합니다. 이어지는 SQL 시뮬레이터(반려동물 인스타그램 게시물 표·댓글 표)는 문장을 직접 써서 FROM → WHERE → GROUP BY → SELECT → ORDER BY → LIMIT 단계를 눈으로 보는 도구입니다. "민수의 오류" 예시 단추가 GROUP BY 규칙 오류를 그대로 재현하므로, 장면 2를 설명할 때 화면에 띄우면 됩니다.

🙋 예상 질문

"SQL을 외워야 하나요?" → "아니요. AI가 짜 준 코드 속 select·insert가 무슨 뜻인지 읽을 수 있으면 됩니다. 외우는 대신 조립기로 문장이 어떻게 만들어지는지 한 번 보세요." · "수파베이스 SQL 편집기에서 직접 실행해 봐도 돼요?" → 학급 공용 프로젝트에서는 학생 계정에 편집기 권한이 없으므로 안 됩니다. 원하는 학생은 자기 개인 프로젝트를 만들어 시험하게 하되, 개인정보가 든 데이터는 넣지 않도록 14차시 기준을 미리 말해 둡니다. · "파이썬 코드에는 GROUP BY가 없는데요?" → 방명록 코드가 쓰는 라이브러리는 표를 통째로 가져온 뒤 파이썬에서 묶습니다. SQL 편집기에서 직접 GROUP BY를 쓰는 것과 결과는 같고, 어느 쪽에서 세느냐만 다릅니다.

정리 — 다음 시간 예고 (45~50′)

🎙️ 멘트 — 갤러리의 정체 공개, 그리고 예고

도입에서 예고한 반전을 회수합니다. “작품을 올리고 서로 피드백을 남긴 우리 갤러리 — 그게 바로 수파베이스입니다. 여러분은 오늘 처음 배운 게 아니라, 한 학기 내내 쓰던 도구의 이름을 오늘 알게 된 거예요.” 이어서 다음 시간을 예고합니다. “오늘 팀과 데이터 후보를 정했습니다. 다음 시간에는 한 학기의 실습 전체를 윤리의 기준으로 점검하고, 그 기준으로 후보를 걸러 주제 카드를 확정합니다.” 공통 수업 전체의 매듭은 다음 시간(데이터 윤리)에서 짓습니다.

🧾 생기부 관찰 지점

질문 설정 — 주제 카드에서 관심사를 "데이터로 답할 수 있는 형태"의 질문으로 스스로 고쳐 쓴 학생(예: "게임이 좋다" → "장르별 이용 시간 데이터로 무엇을 예측할 수 있나"). · 한계 인식 — 데이터 후보를 세 물음, 특히 윤리 관문으로 스스로 걸러 내고 그 이유를 적은 팀. · 개념 연결 — 동시성 확인 장면이나 CSV의 세 벽을 자기 모둠 경험과 연결해 설명한 학생, ③의 빈 칸 차단을 무결성 개념과 스스로 연결한 학생. 주제 카드는 프로젝트 세특의 출발 기록이 되므로 전량 수합·보관하세요.

✅ 13차시 마무리 체크 (교사)

  • 전원 방명록이 작동하는가? (글 저장 + 최신순 목록 — 막힌 학생은 교사 예비 앱으로 구제)
  • 옆 친구 앱에 서로 글을 남겨 동시성을 확인했는가? (오늘의 발견)
  • 접속 정보가 코드가 아니라 비밀 금고에 있는지 확인했는가? (14차시 윤리 점검의 복선)
  • 팀 구성·주제 카드를 마쳤는가, 또는 이월을 공지했는가? (카드 수합·보관)
  • 갤러리가 수파베이스라는 회수 멘트와 다음 시간(데이터 윤리) 예고를 남겼는가?
  • SQL 절의 지필 범위(문장 읽기 · WHERE 없는 갱신·삭제 · GROUP BY 오류의 까닭)를 안내했는가?
  • 프로젝트 첫 시간 안내(카드에서 출발)를 공지했는가?
